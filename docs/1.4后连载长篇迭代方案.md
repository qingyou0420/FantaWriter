## 一、现状判断：连载视角下的核心缺口

这套软件目前的形态是「**一本 5–30 章、一次排完大纲、一口气生成完**」的单本书工具。写百章级连载时，按影响排序有六个结构性缺口：

### ① 模型单档：细腻章与流水任务共用一个模型，且 Opus 中转可能直接打不通

全部 21 种生成任务（正文、续写、改写、摘要、一致性、抽骨架……）都走同一个 `DEEPSEEK_MODEL`（ai.ts:78–80 的 `getDefaultModel`，chatComplete:269 / chatCompleteStream:312 无条件使用）。作者的实际用法是：**细腻正文走 Claude Opus 4.8 的 OpenAI 兼容中转，摘要/检查/抽取等大宗任务走 DeepSeek**——现在只能整体切换，写一章细腻文就要去设置页改一次模型再改回来。更要命的是兼容性：`chatComplete` 与 `chatCompleteStream` **无条件**把 DeepSeek 私有扩展字段 `thinking: { type: "enabled"|"disabled" }` 放进请求体（ai.ts:280–281、345），对字段校验严格的 OpenAI 兼容中转（Claude 系中转常见）会直接 400——即使手动把模型名改成 Opus 也可能一章都生成不出来。

### ② 记忆是「近五章 + 卷摘要」两点式，人物状态没有账本——百章漂移的根源

`buildMemoryPack` 的记忆构成：最近 5 章摘要（memory-pack.ts:109 `summaryLimit = 5`）、上一章尾 1000 字（:110）、角色状态卡=**最近 3 章摘要原文**（:141–144 `rawSummaries.slice(-3)`）、卷摘要（仅当作者手动生成过，page.tsx:1025–1062 是手动按钮）、关键词命中的世界观。也就是说：第 40 章写的「左臂骨折」「改口叫师父」，到第 46 章就彻底滑出记忆窗，除非恰好被写进卷摘要。章摘要提示词（prompts.ts:390–409）也只要求一段 120–250 字散文，人物状态混在叙事里，无法按人物累积。**跨百章的称呼/伤势/关系/位置漂移，目前没有任何机制能接住**，一致性检查只能事后抓，抓到也要人工翻回去改。

### ③ 提示词按「单本完结书」设计：没有钩子概念，反而要求每章起承转合完整

全仓库搜不到「钩子/断章/悬念」任何实现。`OutlineChapter` 没有章末钩子字段（types.ts:158–174 只有 summary/keyPoints/intensityNote/tags/castIds）；大纲生成 JSON 模板不要求钩子（general.ts:61–74）；正文要求第 4 条反而写着「**情节完整、有起承转合，与前后章可衔接**」（general.ts:163）——这是单行本审美，对网文连载是反模式：连载章要「开头接住上章钩子、结尾把读者按在下一章门口」。番茄等平台的追读逻辑全押在章末钩上，这一条提示词等于让模型每章「写圆了」。

### ④ 排章是「一次性全书大纲」，没有按实际写作滚动续订的路径

三条排章路径全是「预先规划」：全书大纲一次生成（建议章数被硬夹在 1–30，SettingsPanel.tsx:215–230、prompts.ts:318–321）；按卷生成大纲一次 3–20 章（general.ts:433），输入只有人物/背景/卷摘要和「前卷终局」（volumes.ts:113–132 只取上卷摘要+上卷末章摘要）；手工加章。**没有任何模式**能做连载最常见的动作：「已写到第 87 章，基于**实际写出来的**前情（章摘要、未回收伏笔、人物现状）续排第 88–100 章」。现在想续排只能重生成本卷大纲——它不读已写正文的摘要，还会警告替换已写章（page.tsx:350–358）。

### ⑤ 「一章一审」没有闭环：审阅机制散在三处、各有断点

连载的日常单位是「生成一章 → 人审一章 → 定稿一章」。现在这条环是散的：大纲↔正文对照要跑去工具页重新选章（ToolsPanel.tsx:123–151）；一致性检查只有全书粒度，`buildConsistencyRows` 不分卷不分段全量拼（consistency.ts:11–31），300 章的书每按一次都是全书摘要重发一遍；章摘要**只能看不能改**（ChaptersReader.tsx:884–910 只有「重新生成摘要」按钮）——摘要是记忆包的地基，AI 摘错了一个称呼，后面每一章都被错误记忆污染，而作者现在无法手改。章也没有「已审/未审」状态（`ChapterContent.status` 只有 idle/generating/done/error，types.ts:209），队列夜里跑完 10 章，第二天分不清哪几章看过了。另有两个真 bug（详见 P1-4）：按拍扩写的增量提交会把**整章摘要覆盖成单拍摘要**；时间线增量是条死管道，提交了也悄悄丢弃。

### ⑥ 连载运营缺口：伏笔无界注入、无存稿概念、导出不按章序、字数档不可自定义

- 伏笔板所有未回收的「读者已知」线索**全量**注入每章（memory-pack.ts:11–17 无上限无筛选）；百章书攒下几十条开放线索后，每章提示词里都是一屏与本章无关的线头，注意力被稀释、费用白涨。也没有「这条埋了 60 章该收了」的到期提醒（`plantChapterId` 字段存在 types.ts:253，但没有任何 UI 用它算悬置时长）。
- 章节导出文件名是 `ch-${chapterId}.md`（export-chapters.ts:106，UUID），磁盘里完全不按章序排。
- 进度页只有字数/目标（progress.ts:42–84），没有存稿数、已发布标记、日更节奏——连载作者最关心的三个数一个都没有。
- 章节字数只有短/中/长三档死值（types.ts:768–772），平台对字数有明确规格（如 2000±300）时无法贴着写。

## 二、P0 —— 立刻做（决定连载可用性）

每项标注涉及面 [代码/功能/体验/UI/提示词与记忆]、文件、动机与完成标准（DoD）。

### P0-1 分档模型：精写档 + 主力档，任务分流；顺手修 thinking 字段兼容 [代码/功能]

- **文件**：`src/lib/ai.ts`（`getDefaultModel`:78–80、`saveApiConfig`:115–166、`chatComplete`:262–290、`chatCompleteStream`:300–382）、`src/app/api/generate/route.ts`（各 mode 分支）、`src/app/api/config/route.ts`、`src/components/AppSettingsMenu.tsx`（API 设置块:518–540 附近）。
- **问题**：见①。单档模型 + 无条件发送 `thinking` 扩展字段。
- **做法**：
  1. `config.env` 增加**可选**精写档三件套：`FINE_API_KEY` / `FINE_BASE_URL` / `FINE_MODEL`（命名与厂商无关，仍走 OpenAI 兼容协议，**不引入 Anthropic SDK、不绑官方 Anthropic 密钥**）。未配置时一切行为与现在完全一致。
  2. 任务分流：`chapter` / `continue` / `rewrite` / `scene_chapter` 走精写档（配置了才走，否则回落主力档）；`chapter_summary` / `consistency_check` / `outline*` / `extract_*` / `learn_style` / `volume_summary` 等大宗任务永远走主力档（DeepSeek）。分流表放 `ai.ts` 单一常量，写测试锁住。
  3. `thinking` 字段只在 `DEEPSEEK_THINKING === "1"` 时才附加到请求体；未开启时**完全不发送该字段**（现在发 `{type:"disabled"}` 也可能被严格中转拒收）。
  4. 设置 → API 设置加一个可折叠的「精写模型（可选）」块（Key/Base URL/模型名三项），`/api/config` 的诊断（ai.ts:82–108）同时报两档的 hasKey/model；`recordUsage`（storage.ts:799）的 byMode 现状已够区分任务，不必再加档位维度。
- **为什么伤连载**：这是作者声明的核心用法。分档前，细腻章要么用便宜模型凑合、要么全书费用按 Opus 计；thinking 字段不修，Opus 中转可能一章都出不来。
- **DoD**：只配主力档时行为与现在逐字节一致（快照断言请求体无 `thinking` 字段、模型名不变）；配了精写档后抓 `chapter` 请求体用 `FINE_MODEL`、`chapter_summary` 仍用 `DEEPSEEK_MODEL`；`DEEPSEEK_THINKING=1` 时 `thinking:{type:"enabled"}` 照发。补 `ai` 层单测覆盖三种 env 组合。

### P0-2 人物状态账本：结构化章摘要，状态卡改为「按人物累积」 [提示词与记忆/功能]

- **文件**：`src/lib/prompts.ts`（`buildChapterSummaryUserPrompt`:390–409、`parseTouchedThreads`:411–424）、`src/app/api/generate/route.ts`（chapter_summary 分支:289–306）、`src/lib/memory-pack.ts`（`buildCharacterStateCard`:79–95、`buildMemoryPack`:101–195）、`src/lib/types.ts`（`NovelProject` / `ChapterContent`）、`src/app/project/[id]/page.tsx`（摘要落地回调:577–618）。
- **问题**：见②。状态卡的原料只是最近 3 章摘要散文，人物状态没有跨章账本。
- **做法**：
  1. `chapter_summary` 的输出升级为「散文摘要 + 结构化附录」：在现有提示词末尾追加一段 JSON 要求——`states: [{ name, location?, injury?, relationsDelta?, addressDelta?, goal? }]`，只写**本章发生变化**的人物、只写正文明写的事实（沿用「触及的伏笔」行的解析套路，parse 失败不阻断散文摘要落地）。
  2. 项目新增 `characterStates?: Record<string, { chapterOrder: number; note: string }[]>`（按人物名滚动追加，每人保留最近 N=6 条），章摘要落地时合并写入；提供整卡手改入口（人物页或伏笔页加一块「当前状态」）。
  3. `buildCharacterStateCard` 改为优先用账本：`【角色状态卡】` 输出每个（本章出场的）人物的最新 2–3 条状态行（带章号），最近 3 章散文摘要降级为补充；无账本数据时行为与现在一致（兼容旧项目）。
  4. 旧章批量补账本：复用「重新生成摘要」通道即可（见 P1-1 的批量补摘要），不必单做迁移。
- **为什么伤连载**：这是「几百章不漂移」唯一可规模化的机制——摘要窗口再怎么加长都是 O(章数) 的输入膨胀，账本是 O(人物数) 的。称呼/伤势/关系是一致性检查抓到的问题里最高频的三类（提示词自己也这么列，prompts.ts:479），事前注入远比事后检查便宜。
- **DoD**：`memory-pack.test.ts` 补断言——第 46 章生成时，状态卡包含第 40 章写入的「左臂骨折」（模拟账本数据）；无账本时输出与现有快照一致；`prompts.test.ts` 锁摘要 JSON 附录格式与 parse 容错；手改状态卡后下一章请求体含手改内容。

### P0-3 连载模式与章末钩子 [提示词与记忆/功能/UI]

- **文件**：`src/lib/types.ts`（`OutlineChapter`:158–174、`GenerationSettings`:132–156）、`src/lib/prompts/general.ts`（`generalOutlineUser`:41–75、`generalVolumeOutlineUser`:423–467、`generalChapterUser` 正文要求:159–165、`generalContinueUser`）、`src/lib/prompts.ts`（`parseOutlineJson`:173–211）、`src/components/OutlinePanel.tsx`（章编辑区:503–555）、`src/components/SettingsPanel.tsx`。
- **问题**：见③。零钩子概念 + 「情节完整起承转合」反模式。
- **做法**：
  1. `OutlineChapter` 增加 `hook?: string`（章末钩子：本章结尾要悬着的事）；两个大纲生成 JSON 模板都要求 `"hook"` 字段；`parseOutlineJson` 解析入库；大纲编辑区加「章末钩子」输入框。
  2. `GenerationSettings` 增加 `serialMode?: boolean`（连载模式，默认关）。开启后正文要求改写为：「开头 1–2 段承接上一章结尾的悬念，不要另起炉灶；结尾必须停在钩子上（本章钩子：{hook}），禁止把冲突写完、禁止总结式收尾」；关闭时逐字保持现状。上一章的 hook 随记忆包注入（`buildMemoryPack` 在「上一章结尾片段」块后附一行「上章钩子：…」）。
  3. 章摘要提示词（P0-2 同一处）在连载模式下追加一问：「本章结尾钩子是否落地，一句话」，写进摘要散文即可，不加字段。
- **为什么伤连载**：钩子是连载追读的生命线；现在模型被明确指示写「完整」的章，作者要靠改写/续写手工掰断，每章多一轮 API 和人工。
- **DoD**：`assemble.test.ts` 断言——serialMode 开启且章有 hook 时，chapter 请求 user 文本含钩子条款与上章钩子行；serialMode 关闭时与现有快照逐字一致；大纲 JSON 快照含 hook 字段；旧项目（无 hook/serialMode）normalize 后不炸。

### P0-4 滚动排章：按实际前情续订下一批章 [功能/提示词与记忆]

- **文件**：`src/lib/prompts/general.ts`（新增 `generalNextChaptersUser`，参考 `generalVolumeOutlineUser`:423–467）、`src/lib/prompts/registry.ts`（新 task `outline_next`）、`src/app/api/generate/route.ts`、`src/app/project/[id]/page.tsx`（新增 handler，参考 `generateVolumeOutline`:345–417）、`src/lib/volumes.ts`（`mergeVolumeChapters`:135–163 可复用尾插逻辑）、`src/components/OutlinePanel.tsx` / `VolumesPanel.tsx`（入口按钮）、`src/lib/types.ts`（`Volume`:28–33）。
- **问题**：见④。没有「基于已写内容续排」的路径；建议章数夹死 30；卷只有一行 summary，没有弧线目标。
- **做法**：
  1. 新任务 `outline_next`：输入 = 卷弧线 + 最近 8–10 章**实际章摘要**（AI 摘要优先，取自 `project.chapters[].summary`）+ 未回收的读者已知伏笔（含「建议尽快回收」标注，见 P1-2）+ 人物状态账本（P0-2）+ 期望续排章数 N（默认 10，上限 20）。输出与现有大纲 JSON 同构（含 hook），**追加**到当前卷尾（复用 `mergeVolumeChapters` 的插位重排），不触碰已有章。
  2. `Volume` 增加可选 `arcGoal?: string`（本卷弧线要达成什么）与 `exitState?: string`（出卷时的局面），分卷面板可编辑；`outline_next` 与 `formatVolumeMemory`（memory-pack.ts:42–73）注入这两项，缺省不显示。
  3. 入口：大纲页与分卷面板各加「续排本卷 N 章」按钮；「建议章节数」文案改为「每次规划章数」，语义从「全书章数」纠正为「单次排章批量」（夹值 1–30 保留，对单次批量是合理上限）。
  4. 全书一次性大纲路径保留不动（短篇/中篇仍是主路径）。
- **为什么伤连载**：连载的大纲永远是活的——写到 87 章时对后 10 章的规划必须基于**写出来的**87 章而不是三个月前的预排。现在唯一的续排手段（重生成本卷大纲）不读实际前情且会威胁替换已写章，作者只能全手工排。
- **DoD**：`assemble.test.ts` 断言 `outline_next` 请求含最近章 AI 摘要与开放伏笔、不含已写正文全文；对 30 章卷续排 10 章后，原 30 章的 id/order/正文关联不变、新章接在卷尾且全书 order 连续（`volumes.test.ts` 补断言）；已挂原作的项目该入口隐藏（与全书一键同一闸，renewal.ts:5–13）。

## 三、P1 —— 接着做（审阅回路与记忆卫生）

### P1-1 章摘要可编辑 + 缺摘要批量补 [体验/UI]

- **文件**：`src/components/ChaptersReader.tsx`（摘要显示区:884–910、`regenerateSummary`:603–630）、`src/components/ToolsPanel.tsx`（或章节侧栏头部）。
- **问题**：摘要是记忆包与一致性检查的地基（memory-pack.ts:117–126、consistency.ts:20），但只能整段重新生成，不能手改；也没有「哪些章缺摘要」的总览与批量补齐（唯一的「一键补」是补字数，ChaptersReader.tsx:873）。
- **做法**：摘要区从 line-clamp 只读文本改为「点击展开 → textarea 手改 → 保存」（写 `ChapterContent.summary`，与重新生成并存）；工具页加「补齐缺失摘要」按钮：串行对所有「有正文但无摘要」的章跑 `chapter_summary`（走主力档，P0-1 后天然便宜），带进度与中断。
- **为什么伤连载**：AI 摘要错一个称呼，之后每章的记忆包都在复读这个错误；批量补摘要是老书迁入（粘贴既有稿）后启用记忆体系的唯一入口。
- **DoD**：手改摘要后 `buildMemoryPack` 输出含手改文本（补单测）；批量补跑完后 `buildConsistencyRows` 全部走摘要分支不再截正文；批量中途失败不覆盖已有摘要。

### P1-2 伏笔注入收敛与「到期」视图 [提示词与记忆/UI]

- **文件**：`src/lib/memory-pack.ts`（`formatPlotThreads`:11–17）、`src/lib/api.ts`（`formatPlotThreadsForPrompt`:179–187）、`src/components/PlotThreadsPanel.tsx`、`src/lib/types.ts`（`PlotThread`:248–260）。
- **问题**：见⑥第一条。全量注入无上限；`plantChapterId` 没人消费；没有回收提醒。
- **做法**：
  1. 注入收敛：`formatPlotThreads` 接受当前章 order，排序规则 = 本章 scenes.threadIds 指名的 > 最近 5 章 touchedThreads 命中的 > 主线（kind=main）> 其余按埋设新近度；截断到 12 条，尾行「（其余 N 条未列出，见伏笔板）」。两处调用（memory-pack.ts:146、api.ts:179）同源。
  2. `PlotThread` 增加可选 `dueChapterOrder?: number`（打算在第几章前回收）；伏笔板列表显示「悬置 N 章」（当前最大已写章 order − 埋设章 order），超过 30 章或过了 due 的标黄置顶。
  3. `outline_next`（P0-4）的输入里，过期线索标注「建议在本批回收」。
- **为什么伤连载**：开放线索是随章数单调增长的，唯一的两个出路是「收敛注入」和「提醒回收」；现在两个都没有，注入是纯噪音增量，回收全靠作者脑内记账。
- **DoD**：`memory-pack.test.ts` 断言 20 条开放线索时注入 ≤12 条且指名线索必在；伏笔板对 plantChapterId 早于 30 章前的条目显示悬置章数（补组件纯函数单测）。

### P1-3 一致性检查分范围与增量 [功能]

- **文件**：`src/lib/consistency.ts`（`buildConsistencyRows`:11–31、`ConsistencyReport` types.ts:227–238）、`src/components/ToolsPanel.tsx`（`runConsistency`:97–121）、`src/app/project/[id]/page.tsx`（`maybeAutoConsistency`:943–973）。
- **问题**：见⑤。永远全书全量；`ConsistencyReport` 不记检查到哪一章，每次都是从头再花一遍钱；300 章时一次检查仅摘要就是几万字输入。
- **做法**：`buildConsistencyRows` 加范围参数 `{ scope: "volume" | "recent" | "all" | "sinceLast", volumeId?, recentCount? }`；工具页加范围下拉（默认「本卷」）；`ConsistencyReport` 增加 `coveredUpTo?: number`（检查覆盖到的章 order），「自上次以来」= 上次 coveredUpTo 之后的章 + 人物卡。队列跑完的自动检查改用「本卷」范围（page.tsx:948 处）。
- **为什么伤连载**：检查频率应该跟连载节奏走（每完成一批查一批）；现在的全书粒度让检查越写越贵、越写越少按。
- **DoD**：`consistency.test.ts` 补范围断言（本卷只含该卷章；sinceLast 只含新章）；报告持久化含 coveredUpTo；旧报告（无该字段）不炸。

### P1-4 修两个真 bug：拍增量覆盖整章摘要、时间线死管道 [代码]

- **文件**：`src/app/project/[id]/page.tsx`（`onCommitBeatDeltas`:1716–1750）、`src/lib/beat-contract.ts`（`proposeBeatDeltas`:143–161）、`src/lib/skeleton.ts`（时间线条目创建:471–473 仅骨架路径有）。
- **问题**（1.4.0 按拍扩写落地后遗留）：
  1. **拍摘要覆盖整章摘要**：`proposeBeatDeltas` 的 `summary` 取的是**单拍** `scene.summary`（beat-contract.ts:156），而 `onCommitBeatDeltas` 直接 `summary: deltas.summary?.trim() || c.summary`（page.tsx:1722）——接受第 3 拍并确认增量后，整章摘要被替换成第 3 拍的一句话，前两拍的事从记忆里消失，后续章的衔接全部失真。
  2. **时间线死管道**：`BeatCommitDeltas.timelineNote` 没有任何生产者（`proposeBeatDeltas` 从不填它），而消费端只在已存在标题为「时间线」的世界观条目时追加（page.tsx:1730–1741 `findIndex` 后 `if (idx >= 0)`），否则**静默丢弃**；从零项目没有任何路径创建该条目（只有骨架写入会建，skeleton.ts:471–473）。字段、UI 文案（「摘要、线索、时间线、物品增量需二次确认」，Changelog 1.4.0）都在，功能是空的。
- **做法**：① 拍增量的摘要改为**追加合并**（`【拍N】…` 逐拍累积），或在全拍接受/跳过后用整章正文跑一次 `chapter_summary` 生成真·章摘要（推荐后者，与从零路径同源）；② `proposeBeatDeltas` 从草稿中抽含时间词的句子作为 timelineNote 候选（保持「人确认才提交」），消费端在「时间线」条目不存在时创建它（复用 `upsertLore` 的套路）。若不想做②的抽取，至少把消费端修为可创建条目 + 在 BeatWorkbench 增量面板给 timelineNote 一个手填输入框。
- **为什么伤连载**：焕新老书正是「原作焕新 → 继续连载」的路径，拍级摘要污染会顺着记忆包扩散到新写的每一章。
- **DoD**：`beat-contract.test.ts` 补断言（多拍提交后章摘要含全部已接受拍的内容；timelineNote 提交后 lore 出现/追加「时间线」条目）；手工路径：接受两拍并确认增量，章摘要不再只剩最后一拍。

### P1-5 章级审阅流：草稿/已审 + 「本章体检」 [功能/UI]

- **文件**：`src/lib/types.ts`（`ChapterContent`:205–224）、`src/components/ChaptersReader.tsx`（头部操作区:820–910、侧栏 `ChapterNavItem`:1434–1477）、`src/components/ToolsPanel.tsx`（`runOutlineCheck`:123–151 逻辑上移复用）。
- **问题**：见⑤。章没有「已审」状态；大纲↔正文对照在工具页要重新选章；队列跑完 10 章后没有任何「哪些没看过」的标记。
- **做法**：
  1. `ChapterContent` 增加 `reviewState?: "draft" | "reviewed"`；AI 生成/续写落稿默认 draft，手动点「标为已审」置 reviewed，之后任何 AI 覆写自动回 draft。侧栏章条目加未审圆点（与现有 StatusDot 并列），侧栏头部显示「N 章未审」。
  2. 正文页头部加「本章体检」按钮：一次跑「大纲↔正文对照」（现有 `outline_vs_content`）+ 篇幅达标（本地）+ canon 冲突（本地 `detectCanonViolations`）+ 摘要是否存在，结果以小卡片显示在正文上方，不跳页。工具页的对照卡保留（全书视角）。
  3. 不做自动多轮改稿循环：体检只报告，改稿仍走现有改写/续写按钮（与既有「提示不阻断」原则一致）。
- **为什么伤连载**：一章一审是作者指定的工作形态；审到哪了必须是数据而不是记忆。体检把三处分散检查折叠成一次点击，是日更路径上按得最频的按钮。
- **DoD**：队列生成 3 章后侧栏出现 3 个未审标记；标已审后重新生成该章回到未审；「本章体检」一次点击产出对照+篇幅+canon 三段结果（体检聚合函数补单测）。

### P1-6 队列限章：「只写下一章」与「写 N 章后暂停」 [功能/UI]

- **文件**：`src/lib/book-job.ts`（`createBookJob`:49–90、`BookJob`）、`src/app/project/[id]/page.tsx`（`startBookJob`:858–896、`runBookJob`:714–856）、`src/components/BookJobBar.tsx`。
- **问题**：队列只有「全书/本卷跑到底」（page.tsx:731 起的 while 循环直到 pending 用尽），与一章一审的节奏相反；顶栏主按钮就是「一键生成正文」（page.tsx:1133–1148），把新用户也引向一口气全书。

- **DoD**：`book-job.test.ts` 补 maxChapters 断言（N 章后 status=paused、剩余仍 pending）；「写下一章」走队列路径（请求体含上一章 AI 摘要的既有时序断言复用）。

### P1-7 出场人物自动化：大纲产 cast、名片封顶 [提示词与记忆]

- **文件**：`src/lib/prompts/general.ts`（大纲 JSON 模板:61–74、459–465）、`src/lib/prompts.ts`（`parseOutlineJson`:190–203 现在写死 `castIds: []`、`formatCharacters`:57–76）、`src/lib/skeleton.ts`（castNames→castIds 的现成映射:523–525 可照抄）。

## 六、明确不做

1. **不绑 Anthropic 官方 SDK/密钥。** 精写档只是第二组 OpenAI 兼容配置，字段命名厂商无关。
2. **不上向量库 / RAG / 嵌入检索。** 人物状态账本、伏笔收敛、滚动排章全部基于已有结构化数据；世界观仍是关键词命中。
3. **不做自动多轮 agent 改稿循环。** 体检/检查只报告不阻断；改稿由人发起。
4. **不做发布平台对接（番茄等无公开作者 API）。** 只做存稿标记、按序导出、纯文本复制这些「贴着发布流程」的本地能力。
5. **不重做已落地项**：焕新护栏、队列时序、存储分键、备份闭环、更新链路本轮全部不碰。
6. **许可证规则**：如引入外部实现，仅吸收 MIT/Apache 代码并在文件头标注出处；GPL/AGPL 项目只研究思路，禁止复制其代码。
7. **不把任何作品设定写死进产品**；`src/` 不出现作品专属常量。
8. **本方案自身不实现**：Fable 5 只出本文档；代码由后续（更便宜的）模型按上述顺序执行，作者看 diff 合入。
