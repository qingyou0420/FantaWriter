## 二、四个 fork 修复：真伪核验

### 2.1 锁：进程内租约 + force-release + 诚实 BOOK_BUSY —— 真，但只接了一半线（引出 B2）

- `packages/core/src/state/manager.ts`：`forceReleaseBookLock()`（190 行起）先 abort 持有者、等 1.5s 宽限、清 `processBookLocks`、unlink 锁文件，**不依赖 abort 成功**；`inspectBookLock()`（183）与 `GET /books/:id/lock`（server.ts 2686）配套；`isStaleProcessLock()`（383）给进程内条目补了「abort 已发 / 心跳超租约」两种回收；`BookWriteLockError` 文案按持锁形态分流，进程内冲突明说「不会自动恢复，去 abort 或 force-release」（83 行），测试还专门断言**不再出现**误导旧文案「Stale locks are recovered automatically」（`state-manager.test.ts` 830–831）。
- `POST /api/v1/books/:id/lock/force-release`（server.ts 2695）存在且有端到端测试（`lock-and-truth.test.ts`：持锁→truth PUT 409 带 owner.taskId→force-release→重试 200，实跑通过）。
- **要点澄清（不是缺陷，但 owner 应知道）**：「进程内 TTL」治不了《醉词》那种**卡死但心跳还活着**的任务——心跳定时器每 30s 刷新 `heartbeatAt`（`startLockHeartbeat`，489–516），租约永远新鲜，`isStaleProcessLock` 永远为假。对挂起任务，真正的恢复手段只有 force-release（及其内部 abort）。错误文案对此是诚实的。
- **缺口**：`acquireBookLock(bookId, holder?)` 的持有者登记（taskId/stage/abort）**没有接进任何管线写路径**——`pipeline/runner.ts` 的全部 8 处取锁（1121、1351、1822、1845、1867、1876、1892、3035）都是裸 `acquireBookLock(bookId)`；全仓唯一传 holder 的产品代码是 truth PUT 的 `{ stage: "truth-put" }`（server.ts 5753）。后果见 B2。
- **附带**：force-release 路由是「abort **进程内全部** activeConfirmedTasks」再释放（server.ts 2700–2706），不是只 abort 目标书的持有者——多书并行时强释 A 书会连坐中止 B 书的聊天生产任务。蓝图 §2.2 写的是「abort 关联任务」。列 M4。

## 三、合并前必修（Blockers）

### B1 · 接管的引擎永远杀不掉：退出与「重启引擎」在崩溃恢复场景双双空转

**症状**：壳崩溃/被强杀后引擎子进程存活（引擎无父进程看门狗，`api/index.ts`/`server.ts` 无任何 ppid 检测——这本身是设计内的，靠下次启动接管）。下次启动 `resolveEngineUrl()` 探测健康、token 匹配、走「接管已有引擎」分支（main.cjs 323–330）——**但该分支不设置 `engineProcess`**。而 `stopEngine()` 第一行是 `if (!engineProcess) return;`（285 行）。于是：

1. **退出不杀接管的引擎**：`before-quit`/`window-all-closed` → `stopEngine()` 直接返回 → 引擎裸留后台。README「退出时……杀掉引擎子进程」对接管场景不成立；
2. **「重启引擎」菜单空转**：`restartEngine()`（416 行）→ `stopEngine()` 空转 → `resolveEngineUrl()` 再次探测到同一个（可能已挂死的）引擎、token 匹配、**再次接管**。蓝图 G0 三层恢复的最后一层「重启引擎＝绝对兜底」恰好在它存在意义的场景（引擎带着卡死任务残留）失效。

**成因指认**：接管分支只回传 URL；`stopEngine` 只处理「本壳 spawn 的 child」。健康端点其实已经回报 `pid`（server.ts 2670），杀掉接管的引擎所需信息是现成的。

**修法建议（二选一）**：接管时记下健康端点回报的 pid，`stopEngine` 对「无 child 但有 pid」的情况走 `POST /engine/shutdown` + 按 pid taskkill；或干脆放弃静默接管——探测到残留引擎一律先结束再重启（蓝图 §4.2 本来要求的是「提示：接管 / 结束并重启引擎」，现实现连提示都没有）。

**波及验收**：蓝图 G0「三层恢复 120 秒内让书恢复可写」「重启引擎后无残留锁文件」两条在接管态不可达成；P0 人工验收「任务管理器无第二个引擎进程」在「旧壳崩溃→新壳启动→用户退出」序列后会失败（那个引擎永远在）。

### B2 · 产品主写章路径不可中止、锁无持有者、强释后产物仍会落盘

**症状**：Studio 里驾驶舱与书详情的「写下一章」按钮（`pages/Dashboard.tsx:275`、`pages/BookDetail.tsx:155`）直连 `POST /api/v1/books/:id/write-next`（server.ts 3350，`/draft` 3370 同病）。该路由 fire-and-forget 地 `pipeline.writeNextChapter(id)`：

1. **不注册 AbortController**：不进 `activeConfirmedTasks`，所以 force-release 的「abort 全部任务」摸不到它；`runner.ts` 的 `runWithAbortSignal`（436 行）在这条路径上无人调用（聊天生产路径是接了的：`agent-tools.ts:894` 把 `signal` 包进 `runWithAgentContext`，server.ts 4920–4968 注册中止器——所以「中止传播」只对聊天任务成立）；
2. **锁不挂持有者**：`writeNextChapter` 内部 `acquireBookLock(bookId)` 裸调（runner.ts 1822），BOOK_BUSY 卡上「任务/阶段」两栏对这条最常见的持锁者永远显示「未知」——蓝图 §2.2「UI 能显示谁持锁、在哪个阶段」对产品写章路径没兑现；
3. **强释后幽灵提交**：force-release 清 map + unlink 后书恢复可写，但这条挂着的管线**还在跑**。它持有的 release 闭包只保证「不误删新锁文件」（manager.ts 303–311 的 token 比对），而 `commitAtomicFileSet` 与结算落盘**没有任何锁所有权复核**（`utils/atomic-file-set.ts` 无 `processBookLocks` 检查）——LLM 一旦恢复响应，旧任务会把整章+状态原子写进书目录，与用户强释后新发起的写章交错，破坏 G0「同一书任一时刻至多一个写入者」。蓝图 R1 说的「强制释放……接受该任务产物作废」在代码里没有对应物：产物不会作废，会照常落盘。

**修法建议**：`write-next`/`draft` 路由为每次运行建 AbortController 注册进 `activeConfirmedTasks`（或专用注册表），用 `pipeline.runWithAbortSignal(controller.signal, …)` 包住，并把 `{ taskId, stage, abort: controller }` 作为 holder 传进管线取锁（runner 的写路径签名加可选 holder 即可，改动集中在 runner.ts 1822 与 3035 两处主入口）；力度更足的兜底是 `commitAtomicFileSet` 前复核本任务仍持有锁 token，不持即弃写。

**波及验收**：G0「人为挂起 LLM 后三层恢复让书恢复可写」字面上能过（force-release 确实能让书**可写**），但恢复后的书面临旧任务的延迟污染；P0 验收「写章中途断网→任务报错终止，锁释放」依赖 undici 超时自然抛错，属可过；「点取消→60 秒内回到可写」在 write-next 路径上没有「取消」可点（无任务实体）。

## 八、结论
