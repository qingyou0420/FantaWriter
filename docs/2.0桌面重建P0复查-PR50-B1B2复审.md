## 〇、一段话结论

**B1 修实了**：新模块 `engine-handle.cjs` 让壳对「自己 spawn 的」与「接管的」引擎走同一条 pid 级杀链，退出与「重启引擎」不再对接管态空转，有 4 个真单测。**B2 对 `write-next` 修实了**：路由注册 AbortController 进 `activeConfirmedTasks`、锁挂 `{taskId, stage, abort}` 具名持有者、force-release 先 abort 持有者且管线在落盘前有中止检查点，BOOK_BUSY 能报出持有者，core/studio 各有真测试（含「强释后 `persistChapterArtifacts` 不被调用」的直接断言）。**但 B2 原文点名的孪生路由 `/draft` 一行未动**——它同样是 BookDetail 上紧挨「写下一章」的产品按钮，`writeDraft` 仍是裸取锁、无中止器、强释后照常把整章+索引+快照落盘，幽灵提交场景对它原样成立。结论：**merge after remaining blockers**——只剩这一个收尾项，改法与 write-next 完全同构。

## 一、B1 核验：接管引擎的杀/重启 —— 已修复（代码+测试）

**代码**：

- 新增 `packages/desktop/lib/engine-handle.cjs`（60 行）：`engineHandle = { child, pid, port, token }` 统一跟踪两种引擎；`adoptEngine()` 强制要求健康端点回报的 `pid`（缺 pid 抛错拒绝接管），`attachSpawnedEngine()` 让 spawn 分支走同一结构；健康端点确实恒定回报 `pid: process.pid`（`packages/studio/src/api/server.ts:2670`，PR #50 首提交就有，本提交依赖成立）。
- 接管分支现在登记 handle（`packages/desktop/main.cjs:353-358`：`adoptEngine(engineHandle, existing, port)`），spawn 分支同样登记（`main.cjs:267`），子进程退出时清理（`main.cjs:273`）。
- `stopEngine()` 重写（`main.cjs:296-335`）：判活改用 `hasLiveEngine(engineHandle)`，先 `POST /engine/shutdown` 优雅关（沿用），然后 Windows 下按 `engineKillPid()` 取到的 pid `taskkill /f /t`，非 Windows 无 child 时按 pid `SIGTERM`→400ms→`SIGKILL`。前次 B1 的死因——`if (!engineProcess) return;` 对接管态直接返回——已不存在。
- 调用点闭环：`before-quit`（`main.cjs:948-953`）、`window-all-closed`（954-957）、`restartEngine()`（446-451）都走这条 `stopEngine`；重启后 `resolveEngineUrl()` 对已被杀死的旧端口探测失败会转入 `canBindPort`→重新 spawn，不再无限重接管。

**测试**：`packages/desktop/tests/engine-handle.test.ts` 4 个用例，第一个就点名复现修复前的 bug（「does not treat an empty handle as stoppable (the pre-fix adopt bug)」），另有接管态 pid/port/token 跟踪、缺 pid 拒接管、spawn/adopt 同路径共 4 条断言链，实跑通过。

**残留观察（非阻塞）**：`main.cjs` 的退出/重启序列本体仍无集成测试（前次 M10 原样）；Windows 下 `taskkill` 是 fire-and-forget，`restartEngine` 紧接着的健康探测理论上可能撞上「正在死」的旧引擎——但优雅 shutdown 已先行、探测多在其后，判为注记级。

## 二、B2 核验：write-next 可中止 + 具名持锁 —— 已修复；`/draft` 孪生路由未修

### 2.1 write-next：三个症状逐一对账（全修）

前次 B2 列了三个症状，逐条对到代码：

1. **「不注册 AbortController」→ 已修**：路由（`packages/studio/src/api/server.ts:3350-3431`）现在为每次运行建 `taskId = write-next-{id}-{uuid}` 与 `AbortController`，注册进 `activeConfirmedTasks`（3365-3367）——force-release 路由的「abort 全部任务」现在摸得到它；同时整个管线跑在 `runWithAgentContext({ signal, abort, lockTaskId, onLocked })` 里，`agentCtxFor` 把 `currentAbortSignal()`（现含 `abort.signal`，`runner.ts:474-476`）传给全部 agent，在途 LLM 请求可被中止。
2. **「锁不挂持有者」→ 已修**：`writeNextChapter` 与 `writeChapters` 两个主入口（前次点名的 runner.ts 1822 与 3035）现取锁为 `acquireBookLock(bookId, this.writeLockHolder("write-next"))`（现 `runner.ts:1864、1901`），holder 含 `{taskId, stage, abort}`；裸调这两个入口时会自包一层 AbortController（`runner.ts:1852-1861、1889-1898`），所以 CLI 等旁路调用也有持有者。BOOK_BUSY 双保险：路由先 `inspectBookLock` 预检并抛带 owner 的 `BookWriteLockError`（3356-3364），竞态下管线内取锁失败经 `lockReady` 的 reject 同样以 409 返回（3403-3406、3423-3427）——响应从 fire-and-forget 改为等锁到手才回 200。
3. **「强释后幽灵提交」→ 已修（abort 传播方案）**：`forceReleaseBookLock` 第一步同步 `holder.abort.abort()`（`manager.ts:199`，不依赖成功）；管线在写手返回后（`runner.ts:2106`）与「落盘最终章节」前（2184-2185）有 `throwIfOperationAborted()` 检查点，`persistChapterArtifacts`（2368）在检查点之后——即使 LLM 客户端无视信号迟到返回，产物也会在提交前被弃。未做前次建议的「更足力度」版（`commitAtomicFileSet` 前复核锁 token），但前次修法建议本就以 abort 注册+holder 为达标线，检查点位置使残余竞态窗口只剩「检查点通过后到写完盘之间」毫秒级，且 force-release 有 1.5s 宽限先行，判为达标。

**测试是真的**：`packages/core/src/__tests__/write-next-lock.test.ts` 3 个用例——holder 具名断言（spy `acquireBookLock` 收到 `{taskId, stage:"write-next", abort}`）；**强释后不落盘**（在 `onLocked` 里触发 `forceReleaseBookLock`，断言管线以 AbortError 收场、spy 的 `persistChapterArtifacts` 零调用、锁已清）；二写碰撞时 BOOK_BUSY 的 `owner.taskId/stage` 具名。`packages/studio/src/api/lock-and-truth.test.ts:116-137` 新增端到端用例：持锁下 POST write-next 得 409，`error.owner.taskId`、`error.message` 都点名持有者。全部实跑通过。

### 2.2 剩余阻塞项：`/draft` 路由与 `writeDraft` 原样未动

前次 B2 原文明确写着「（server.ts 3350，`/draft` 3370 同病）」，修法建议第一句就是「`write-next`/`draft` 路由为每次运行建 AbortController……」。本提交只修了 write-next：

- 路由侧：`POST /api/v1/books/:id/draft`（现 `server.ts:3433-3450`）仍是修复前的 fire-and-forget 原样——不建 taskId、不注册 `activeConfirmedTasks`、不等锁、无 BOOK_BUSY 预检。
- 管线侧：`writeDraft` 入口仍是裸 `acquireBookLock(bookId)`（`runner.ts:1151`），无 holder、无自包 AbortController——它不经过 2.1 修好的两个入口。
- 它不是死代码，而是产品路径：BookDetail 上「写草稿」按钮紧挨「写下一章」（`packages/studio/src/pages/BookDetail.tsx:162-168` 的 `handleDraft` → 491-495 的按钮），且 `writeDraft` 会实打实把整章文件+章节索引+状态快照写进书目录（`runner.ts:1209-1248`：`writer.saveChapter` + `saveChapterIndex` + `snapshotState`）。

后果：B2 的三个症状对这条路径原样成立——挂起的草稿任务 force-release 中止不了（holder 无 abort，`activeConfirmedTasks` 里没有它）；它持锁时 BOOK_BUSY 报「未知」持有者；强释后 LLM 迟到返回时整章照常落盘，与新写入者竞态，G0「同一书任一时刻至多一个写入者」在这条一键可达的产品路径上仍会破。CHANGELOG 对此是诚实的（只写了「写下一章」），但诚实不等于修完。

**修法**：与 write-next 完全同构，两处小改——`/draft` 路由复制 write-next 的注册+等锁模板（或直接抽成共用函数），`writeDraft` 开头加与 `runner.ts:1852-1861` 相同的自包分支并把取锁改成 `this.writeLockHolder("draft")`。加一个仿 `write-next-lock.test.ts` 的 draft 用例即可。

**明确不算阻塞的**（与前次口径一致）：`runner.ts:1381、1924、1933、1949、3092` 等其余裸取锁点前次即归为「缺口说明」而非 blocker，本次不升级；force-release 连坐 abort 全进程任务（M4）、BookBusyCard 缺层级（M3）等 M 项均未动，维持非阻塞。

## 三、结论

**verdict：merge after remaining blockers。** B1 已按前次要求修实（代码+测试均真，`engine-handle.cjs` + `main.cjs` + 4 单测）；B2 在 write-next 主路径上修实（注册中止器、具名持锁、强释即弃写，core/studio 共 4 个新测试直接覆盖三个原症状），但前次 blocker 原文点名的 `/draft` 孪生路由未修，幽灵提交场景在 BookDetail 的「写草稿」按钮上仍一键可复现。剩余工作量极小（`server.ts:3433` 路由套用 write-next 模板 + `runner.ts:1151` 换具名取锁 + 一个测试），修完即可合并。启动路径无 1.x 回归，本次不重开 P1/P2。
