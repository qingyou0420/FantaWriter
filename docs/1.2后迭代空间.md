## 一、现状判断：1.2.0 之后最大的剩余问题

按影响排序。前三条全部围绕一个主题：**这本书的十几万字只存在于一个浏览器源（origin）的 IndexedDB 里，而现在有三条路能让它悄悄丢或悄悄看不见。**

### ① 端口漂移会换掉 IndexedDB 的家（P0-6 做完后新露出来的洞）

1.2.0 的桌面壳端口探测（`electron/main.cjs:101–109` 的 `pickListenPort`）在 17831 被占时静默 +1 递增，把实际端口传给 `loadURL`（`main.cjs:264–267`）。但 **IndexedDB / localStorage 按源（scheme://host:port）分区**：窗口一旦加载 `http://127.0.0.1:17832`，`fantasy-writer` 库（storage.ts:31）就在另一个源里——用户看到的是一个全新空白应用，全部项目"消失"；等下次 17831 空出来又"回来了"。对写了几十章的作者，这是最吓人的一种故障：数据没坏，但表现完全等同丢档。修端口占用（1.2.0 P0-6）是对的，但它把"起不来"换成了"起来了但像丢档"，后者更糟。

### ② 保存失败静默，「已自动保存」可能在说谎

`persistProjects` 的失败只写进模块级变量：`storage.ts:242–244` 把异常记入 `lastStorageError`——而 `getLastStorageError()`（storage.ts:146）**在整个 UI 里零调用方**（已 grep 确认）。与此同时 `useProjectStore.ts:73–78` 在防抖回调里无条件 `setSaveHint("已自动保存")`，与真实落盘结果完全脱钩。叠加两个放大器：

- `lsSet`（storage.ts:75–82）静默吞 quota 异常，而 `persistProjects` 每次把**全部项目的完整 JSON**（含每章最多 12 份版本快照，types.ts:331）镜像进 localStorage——长篇后期轻松超出 5MB 配额，镜像从某天起悄悄停更；
- `initStorage` 的 catch 兜底（storage.ts:206–217）恰恰会回退去读这份可能已过期数月的 LS 镜像——IDB 一旦读失败，用户拿到的是**静默回档**的旧数据。

### ③ 备份链路是半环：能出不能进

- `importFullBackup`（storage.ts:281–371）写得很完整（项目去重、标签/文风/用量合并），但**没有任何 UI 调用它**——「下载完整备份 JSON」（AppSettingsMenu:446、ToolsPanel:644）导出的文件，在应用里没有入口能导回来；首页「导入项目」走的是 `importProjectJson`（app/page.tsx:162），遇到完整备份的 `{projects:[...]}` 结构直接报「无效的项目文件」。
- 6 小时自动备份只有单槽覆盖写（storage.ts:611–637），且 UI 只能「查看」（ToolsPanel:173–180 只显示时间和数量），**没有恢复按钮**。
- 自动备份与主库同在一个 IndexedDB——浏览器清数据 / 换机 / 上文①的换源，主库和备份一起不可见。桌面端明明有文件系统（`main.cjs:820` 的 `fs:writeTextFiles` 白名单机制现成），备份却没落过盘。

### ④ 全书队列的章摘要慢一拍（卷摘要进记忆做完后新露出来的洞）

`generateChapter` 里章摘要是 fire-and-forget（page.tsx:518–554 的 `void postGenerate({mode:"chapter_summary"...})`），而 `runBookJob` 在拿到 `"done"` 后**立即**开始下一章（page.tsx:717）。下一章组记忆包时（memory-pack.ts:116–125），第 N 章的 AI 摘要几乎必然还在路上，只能回退到**大纲摘要或正文头 200 字**。更要紧的是角色状态卡的原料 `rawSummaries` 只收 AI 摘要或大纲摘要（memory-pack.ts:123–124）——大纲摘要是"计划"不是"实际写了什么"，正文一偏离大纲，夜里跑队列时每一章的状态卡都在用错误的近况。手动逐章生成时用户会停留、摘要来得及落地，所以这个洞只在长篇作者最依赖的**过夜队列**场景发作。

### ⑤ 自动一致性检查指向一个空页面

`maybeAutoConsistency`（page.tsx:872–910）三处与手动路径（ToolsPanel:101–141，1.2.0 P2-3 已修好）脱节：

- 构造的 rows **不带 `summary` 字段**（page.tsx:880–886），提示词模板"优先章摘要"的优化对它无效，全部退化为截 1200 字正文；
- `rows.slice(0, 12)`（page.tsx:896）——60 章的书自动检查只看前 12 章；
- 结果只拼进一条 info 文案，随后 `setTab("tools")`，但工具页的 `consistency` 是组件内 `useState`（ToolsPanel:53–63），**自动检查的结果根本没传进去**，「可在「工具」页查看详情」是一句空话；且工具页是条件渲染（page.tsx:1482），手动检查的结果切一次 tab 也全部丢失——一次几万 token 的检查经不起一次误触。

### ⑥ 中转挂起没有任何护栏（5xx 重试做完后新露出来的洞）

1.2.0 的瞬时错误重试只对**已经报错**的请求生效。而大陆中转最常见的另一种故障是**挂起**：连接建立、迟迟不吐字。现在三层都没有防线——`new OpenAI({...})`（ai.ts:210–215）没配 timeout（SDK 默认 10 分钟）；`chatCompleteStream`（ai.ts:324–333）对"无增量"没有看门狗；客户端 `streamGenerate`（api.ts:94–128）在流被中间设备安静掐断（EOF 但从未收到 `done:true` 事件，见 route.ts:138–140 只有正常完成才发）时**把半截正文当成功返回**——章被标成 done，截断静默过审（只有低于篇幅下限时才被 `chapterBelowMin` 兜住）。夜里队列停在一个挂死的请求上最长 10 分钟，然后可能以半章"成功"收场。

### ⑦ 崩溃/刷新后，跑到一半的队列在 UI 里卡死

`bookJob` 随项目持久化，崩溃或刷新后 `status` 停在 `"running"`。挂载时没有任何归一逻辑（已 grep：`prepareJobForResume` 只被「续跑」按钮调用），而 `BookJobBar` 对 `running` 只渲染「暂停/跳过」（BookJobBar.tsx:94–112）——两个按钮此时都是空操作（`abortRef` 为 null）；「续跑」要求 `paused/error/idle`、「关闭」要求 `done/error/paused`（BookJobBar.tsx:113–145），全都不出现。用户唯一的出路是再点一次「一键生成正文」新建队列——能走通，但界面上是一个按什么都没反应的僵尸进度条。

### ⑧ 规模问题：提示词和存储都在按"5 章的书"设计

- `generalChapterUser` 把**全书大纲逐章全量**注入每次正文请求（general.ts:87–92、113）：60 章 × 3–6 句摘要 ≈ 每次请求固定多出近万字，费用随书长线性涨、注意力被稀释，本卷之外的细节其实只需要一行；
- `persistProjects`（storage.ts:230–236）每次防抖保存（280ms，useProjectStore.ts:73）把**全库所有项目**重新 `JSON.stringify` 并整体写 LS + IDB——书越写越大，打字越写越卡，这是主线程上的 O(全库) 序列化。

其余（章节列表不分卷、替换不压版本、thinking 下温度滑杆失效无提示、`window.prompt` 编辑卷摘要等）属体验刺，进 P2。

## 二、迭代项（按优先级）

每项标注涉及面 [代码/功能/体验/UI]、文件、动机与完成标准（DoD）。原则不变：先堵"数据会不会悄悄丢/悄悄错"，再修"夜里跑队列的正确性"，最后做界面。

### P0 —— 立刻做（数据安全）

**P0-1 端口漂移不许换数据的家** [代码/体验]
- 文件：`electron/main.cjs`（`pickListenPort`:101–109、`resolveAppUrl`:256–268）。
- 做法：把首次成功使用的端口写进 `config.env`（如 `APP_DATA_PORT=17831`），以后启动**只认这个端口**；被占时不再静默 +1，而是弹阻断对话框讲人话：「端口 17831 被其它程序占用，你的本地数据绑定在该端口上。请关闭占用程序后点重试」，给「重试 / 退出」按钮（循环探测直到可绑定）。只有**首次运行**（config.env 还没记过端口）才允许递增选口。
- 为什么：见①。数据按源分区是浏览器铁律，换端口=换库；"换个端口照常启动"对本产品是伪可用。
- DoD：先占住 17831 再启动——出现指向占用的中文对话框而非空白新库；关闭占用程序点重试后，原有项目全部在；首次安装在 17831 被占的机器上仍能完成初始化并从此固定所选端口。

**P0-2 保存失败要喊出来** [代码/体验]
- 文件：`src/lib/storage.ts`（`persistProjects`:230–236、`lastStorageError`:48/146）、`src/hooks/useProjectStore.ts`（saveHint:73–78）、`src/app/project/[id]/page.tsx`（顶栏 status-pill:1025–1038）。
- 做法：`saveHint` 改为跟 `persistChain` 的真实结果走——写入成功才显示「已自动保存」，`lastStorageError` 非空时顶栏出红色「保存失败」pill，点击展开诊断（quota / IDB 异常原文）并给「立即下载完整备份」按钮；`lsSet` 的 quota 吞异常改为记入同一错误通道。LS 镜像降级为「只存项目元数据（id/名称/更新时间）」或写入时带时间戳、`initStorage` 兜底读到过期镜像（比 IDB 记录时间早）时明确提示"这是 X 天前的降级快照"而不是静默当现役数据。
- 为什么：见②。单人写作最贵的是正文，静默写失败 + 谎报"已保存"是数据丢失的完整配方。
- DoD：用 devtools 模拟 IDB 写失败——顶栏变红、能一键导出备份；正常路径提示与现在一致；`storage.test.ts` 补「persist 失败可被查询」断言。

**P0-3 备份闭环：能导回、能恢复、桌面落盘** [功能/体验]
- 文件：`src/lib/storage.ts`（`importFullBackup`:281、`getAutoBackup`:639、`maybeAutoBackup`:611）、`src/components/AppSettingsMenu.tsx`（菜单:431–452）、`src/components/ToolsPanel.tsx`（备份卡:634–661）、`electron/main.cjs` + `preload.cjs`（新增或复用文件写 IPC）。
- 做法：三件事。(1) 设置菜单加「导入完整备份…」，文件选择后调 `importFullBackup`（它本身已做去重合并），首页「导入项目」在解析失败时识别 `{projects:[...]}` 结构并提示"这是完整备份，请走导入完整备份"；(2) 工具页「查看自动备份」旁加「从自动备份恢复…」，恢复前先把当前库快照存入 `pre-restore-backup` 键再覆盖，confirm 写清后果；(3) 桌面端 `maybeAutoBackup` 同时把 JSON 写到 `userData/backups/`，按日期滚动保留最近 7 份（新 IPC，目录固定白名单，与 `app:openPath` 白名单打通以便「打开备份文件夹」）。
- 为什么：见③。①②再怎么修也挡不住浏览器清数据和硬件故障，落盘 + 可恢复才是底。
- DoD：导出的完整备份能在清空数据的环境导回且项目数一致；自动备份一键恢复可用且有恢复前快照；桌面端 `userData/backups/` 有滚动 JSON，测试断言保留份数。

### P1 —— 接着做（队列正确性与规模）

**P1-1 队列里章摘要先落地再开下一章** [代码/功能]
- 文件：`src/app/project/[id]/page.tsx`（`generateChapter` 摘要分支:518–554、`runBookJob`:717–728）。
- 做法：`generateChapter` 把摘要 promise 存进返回值或 ref；`runBookJob` 在 `result === "done"` 后 `await` 它（设 15–20s 上限，超时/失败不阻断队列，只把该章标记"无摘要"）。顺带：摘要失败时现在写空串（page.tsx:551），改为保留旧摘要并在章卡显示「摘要生成失败，点击重试」（`regenerateSummary` 按钮已有，ChaptersReader:838–851，只差失败状态展示）。
- 为什么：见④。群像长篇的连贯性全押在"上一章实际发生了什么"上，过夜队列恰好是最依赖它、目前最缺它的场景。
- DoD：队列模式下抓第 N+1 章请求体，`previousSummaries` 含第 N 章 AI 摘要（可在 `runBookJob` 路径的测试里 mock postGenerate 断言时序）；摘要接口挂掉时队列不停。

**P1-2 自动一致性检查修到与手动同源，结果落地** [代码/功能]
- 文件：`src/app/project/[id]/page.tsx`（`maybeAutoConsistency`:872–910）、`src/components/ToolsPanel.tsx`（consistency state:53–63、`runConsistency`:101–141）。
- 做法：提取共用的 rows 构造（带 `summary`，不截 12 章——1.2.0 P2-3 已把采样改为"优先摘要"，自动路径带上摘要后整书体量可控）；检查结果（score/summary/issues/时间戳）写进项目数据（如 `project.lastConsistencyReport`）或至少 localStorage，工具页初始渲染显示「上次检查：时间 + 评分」，自动与手动写同一处；info 文案指向的"详情"从此真实存在。
- 为什么：见⑤。这是"做完 P2-3 后新露出来的洞"：手动路径修好了，自动路径还是老样子，而且结果不落地让每次检查都是一次性消费。
- DoD：勾选自动检查跑完 30 章的书——请求体带全部章的摘要行；跳到工具页能看到本次 issues 列表；切 tab 再回来结果还在；补单测断言 rows 构造含 summary 且不截断。

**P1-3 无主 running 队列自动归位** [代码/体验]
- 文件：`src/app/project/[id]/page.tsx`（项目加载处，`ready` 分支附近:922 前后）、可选 `src/lib/book-job.ts` 加 `normalizeStaleJob`。
- 做法：项目加载完成时，若 `bookJob.status === "running"` 而 `jobControlRef.current.running === false`，调 `prepareJobForResume` 变体把 running 项归 pending、job 置 `paused` 并 `setBookJob`——BookJobBar 立即出现「续跑/关闭」。
- 为什么：见⑦。崩溃后第一眼看到的僵尸进度条，是对"这软件靠不靠谱"的直接打击。
- DoD：手工把项目 JSON 的 bookJob 置 running 后刷新——进度条显示"已暂停"，续跑从中断章继续；`book-job.test.ts` 补归一断言。

**P1-4 中转挂起看门狗 + 截断不算成功** [代码/功能]
- 文件：`src/lib/ai.ts`（client 构造:210–215、`chatCompleteStream`:288–345）、`src/app/api/generate/route.ts`（`streamResponse`:121–162）、`src/lib/api.ts`（`streamGenerate`:94–130）。
- 做法：(1) `new OpenAI({ timeout: 120_000 })` 级别的总超时（非流式请求受益）；(2) `chatCompleteStream` 加"无增量看门狗"——连续 90s 没有新 delta 就主动 abort 并抛「中转长时间无响应」（message 命中 `isTransientAiError` 的 timeout 分支，自动接上 1.2.0 已有的队列重试）；(3) SSE 协议补完整性：`streamResponse` 正常结束必发 `done`，`streamGenerate` 在 EOF 而未见 `done:true` 时抛「流意外中断，正文可能不完整」而不是静默返回半截（partial 仍会按现有 catch 逻辑保留进正文，行为不回退）。
- 为什么：见⑥。5xx 重试（1.2.0 P0-4）只治"报错"，不治"挂着不动"和"安静截断"——后两种恰是中转的常见死法。
- DoD：mock 一个只发一半就断的 SSE——客户端报错且失败章可重试，不出现被标 done 的半截章；mock 挂起 90s+——请求被掐断并触发队列自动重试；正常长章生成不误杀（看门狗计时按"距上次 delta"算）。

**P1-5 大纲注入分层：本卷详、他卷一行** [代码/功能]
- 文件：`src/lib/prompts/general.ts`（`generalChapterUser`:77–128 的 `allChapters`）、`src/lib/prompts/registry.ts`（chapter 分支透传 volumes）。
- 做法：当前章所在卷的章目仍全量（标题+摘要+标签）；其它卷收敛为「《卷名》：卷摘要（无则该卷 premise 或首末章标题）」一行一卷；无分卷或总章数 ≤ 15 时行为与现在完全一致。`continue`/`scene_chapter` 不受影响（它们本就不带全书大纲）。
- 为什么：见⑧。这是"卷摘要进记忆"落地后顺理成章的下一步：卷摘要既然有了、还能一键生成（1.2.0 P1-4），全书大纲就不必再逐章平铺。60 章的书每章请求省约 8–9 千字输入，费用与漂移风险同降。
- DoD：`assemble.test.ts` 补断言：三卷 30 章项目生成第 25 章时，第三卷逐章可见、第一二卷各只有一行；≤15 章项目输出与现在逐字一致。

**P1-6 持久化按项目分粒度** [代码]
- 文件：`src/lib/storage.ts`（`persistProjects`:230–236、`readIdbProjects`/`writeIdbProjects`:110–129）、`src/lib/idb.ts`。
- 做法：IDB 从单键 `projects` 数组改为按 `project:{id}` 一键一项目（保留读旧单键的迁移路径，首次启动整体搬迁 + 留 `migration-backup-v3` 快照，照抄 v2 迁移的成熟做法）；`saveProjects` 只写发生变化的项目（`upsertProject` 已知道是哪个）；LS 全文镜像按 P0-2 的决定降级为元数据。
- 为什么：见⑧。280ms 防抖内全库 stringify 是随书长线性变卡的主因，也是 quota 问题的根源；改粒度一并解决两者。
- DoD：`storage.test.ts` 补迁移断言（旧单键数据启动后可读、新键结构就位）；打一个 5MB 的假项目，编辑另一个小项目时不触碰大项目的键（可 spy idbSet 断言）；全量导出/导入不受影响。

### P2 —— 接着的接着（体验与界面）

**P2-1 章节导航按卷分组 + 字数** [UI]
- 文件：`src/components/ChaptersReader.tsx`（侧栏列表:680–710）、`src/components/OutlinePanel.tsx`（章节目录:340–413）。
- 做法：两处列表用现成的 `chaptersGroupedByVolume`（volumes.ts:91）加卷标题分组行（工具页目录预览 ToolsPanel:314–347 已是这个样子，照搬）；正文侧栏每章标题下加当前字数（数据在 `project.chapters`，`countChapterChars` 现成）。多卷才显示分组，单卷不变。
- 为什么：五卷六十章的书，flat 列表找章全靠滚；字数是"哪章偏短"最快的巡检信号（进度页有，但写作现场在侧栏）。
- DoD：多卷项目侧栏与大纲目录出现卷分组头；单卷项目 UI 与现在一致；不引虚拟化。

**P2-2 替换操作的版本护栏与作用域** [功能/体验]
- 文件：`src/components/ChaptersReader.tsx`（`replaceOne`/`replaceAll`:247–264）、`src/components/GlobalFindReplace.tsx`。
- 做法：单章「全部替换」走 `onContentChange(..., { pushVersion: "replace" })`（单处替换不必压栈）；全书查找替换加两个勾选「同时替换章节摘要」「同时替换大纲（标题/摘要/关键点）」——群像改名是它的主用途，摘要和大纲里的旧名不改，记忆包会一直把旧名注回提示词。人物卡/伏笔不自动改，命中时列出来提醒手动处理即可。
- 为什么：全书改名后旧名从摘要里回流，是一致性检查抓不完的慢性漂移源；批量替换无版本快照则是唯一没护栏的批量写操作（全局替换有 pushVersion，单章的反而没有）。
- DoD：单章全部替换后版本列表多一条可恢复快照；勾选摘要作用域改名后，`buildMemoryPack` 输出不再含旧名（补单测）。

**P2-3 thinking 开启时温度滑杆明说无效** [UI]
- 文件：`src/components/SettingsPanel.tsx`（温度 Field:172–191）、数据源用 `/api/config` 的 `thinkingEnabled`（AppSettingsMenu:503–507 已在读）。
- 做法：`DEEPSEEK_THINKING=1` 时滑杆置灰 + 注明「推理模式下模型忽略温度（ai.ts 不传 temperature）」。
- 为什么：ai.ts:269/307–309 在 thinking 时把 temperature 置 undefined，1.2.0 P1-3 的滑杆此时是安慰剂——调了没效果比没有滑杆更误导。
- DoD：置环境变量后设置页滑杆禁用且有说明；关掉后恢复可调。

**P2-4 两处小 UI 刺** [UI]
- 文件：`src/app/project/[id]/page.tsx`（`window.prompt` 编辑卷摘要:993）、`src/components/ChaptersReader.tsx`（自定义改写输入:1202–1208、续写方向输入:1225–1231）。
- 做法：卷摘要确认从 `window.prompt`（单行、不能换行、Electron 下样式突兀）换成分卷面板内联 textarea + 保存/放弃两按钮；两个裸输入框补 placeholder（「自定义改写要求，如：改成雨夜」「续写方向（可空）」）。
- DoD：卷摘要可多行编辑后保存；两输入框空态可自解释。

**P2-5 工程卫生三小件** [代码]

## 三、明确不做的事

1. **不合回双写作台、不做第三台。** `WritingBoard` 保持 `"general"` 单值，`ContentRating` 维持 unrated 死字段（types.ts:72–73 注释即约束）。
2. **不把《醉词》写死进产品。** 卷结构、人物、文风档案一律走项目数据；`src/` 不出现任何作品专属常量。
3. **不把密钥/令牌写进仓库。** API Key 与 GitHub 更新令牌只在本机 `config.env`/`.env.local`；release 的「Refuse secrets in standalone」闸保留；`.env.example` 只放占位符。
4. **不用 Fable 5（或任何代理）直接改功能代码。** 本文只产出文档；`src/`、`electron/`、打包脚本的改动由作者自己动手、看着 diff 合。
5. **不上向量库/RAG/嵌入检索。** 名称关键词 + 区段推进的检索够用；P1-5 的大纲分层也纯靠已有结构化数据，不引检索。
6. **不重做已完成项。** 上一轮 P0–P2 十九项与旧 P0 五项不再触碰；本文所有条目均为新洞或其"下半步"。
7. **不换框架、不上服务端数据库、不做账号/多端同步。** P1-6 只是 IndexedDB 内部的键粒度调整，仍是单机本地存储。
8. **不做自动多轮 agent 改稿循环。** canon 后置检测与一致性检查维持"提示不阻断"。
9. **不重构更新链路。** GitHub Release 更新与 sha256 校验已就位，本轮不动；P0-1 只动端口选择，不碰更新。
10. **不做长列表虚拟化、不做精确 token 计费。** 几十章的规模不值得引依赖；用量统计维持"本地粗估"的定位。
