## 〇、一段话结论

幻想作家 1.6.0 的形态仍是「生成下一章的工具 + 外挂的大纲/禁写/账本」：三段式顶部页签（设定/创作/检视）、以「写下一章 / 一键生成正文」为主 CTA、定稿四件套向导收尾。这与需求方向（一个像 OpenWrite Studio 那样的**创作工作台**）存在代差。本迭代**退役旧主流程**，换成 OpenWrite 的基本流：

```text
灵感/素材 → 规划 Agent 整理人物/设定/大纲 → 作者经 diff 闸确认可写资产
→ 写作 Agent：写前检查 → 组装有界上下文 packet → 写章 → 审稿 → 修订 → 状态结算
→ Markdown / TXT / EPUB 导出
```

界面换成左侧导航的多工作区布局（总览 / 大纲 / 正文 / 审稿 / 资料库 / AI 协作 / 工具与设置 + 右侧创作助手栏）。数据模型引入「正典（canon）/ 运行态（runtime）」分离与整章事务提交。好消息是：1.4–1.6 已发货的记忆包、章契约、状态账本、钩子、滚动排章、分档模型、章版本栈，都是新管线的现成零件——这次迭代主要是**重排交互与补齐闸门/审稿/结算**，不是推倒重写引擎。

## 一、决定：旧主流程退役，OpenWrite 式流程成为唯一主流程

### 1.1 判死刑的交互与入口

以下入口**不再是主路径**。处置分两档：【删】= 本迭代直接移除；【降】= 功能保留但从主 CTA/主导航降级为工具或后台能力。

| 现状入口 | 位置（真实文件） | 处置 |
|---|---|---|
| 三段式顶部导航「设定 / 创作 / 检视」+ 二级页签 | `src/app/project/[id]/page.tsx` + `src/lib/project-tabs.ts`（`StageId`、`stageOf`） | 【删】换成左侧工作区导航（见第二节） |
| 顶栏主 CTA「一键生成正文」（整书队列） | `page.tsx` 顶栏（非 serialMode 时的 primary）→ `startBookJob("missing")` | 【删】主 CTA 变为「写下一章」（新管线）。整书/本卷批量队列（`src/lib/book-job.ts`、`BookJobBar`）**降**入「工具与设置 → 批量任务」，且每章仍走新管线的完整闸门 |
| 「本章契约」面板作为写前手工闸 | `src/components/ChapterContractPanel.tsx`（`contractChapterId` 打开） | 【降】契约的**数据**（goal/hook/cast/forbid，`src/lib/chapter-contract.ts`）并入新管线的「写前检查 + 本章指导」对话框；独立面板退场 |
| 「定稿四件套」向导 | `src/components/FinalizePanel.tsx` + `projectAfterFinalize` | 【删】被「审稿 → 修订 → 状态结算」闭环取代；`finalize-chapter.ts` 里的落账逻辑改造为结算阶段的实现 |
| 「原作焕新」作为首页并列创建模式 | `src/app/page.tsx` 创建卡（scratch/renew 两 tab）、`OriginalPanel`、`BeatWorkbench` 按拍扩写 | 【降】改挂到「工具与设置 → 项目迁移」：导入旧稿 → 解析卷章 → 入库为正文与正典候选（对齐 OpenWrite 的项目迁移语义）。抽骨架/按拍扩写代码保留但不再出现在主导航 |

| 检视段的「plot / tools」页签 | `PlotThreadsPanel`、`ToolsPanel` | 【降】伏笔板并入「资料库」，工具页并入「工具与设置」工作区 |

### 1.2 明确保留（新流程的零件）

- 记忆包 `buildMemoryPack`（`src/lib/memory-pack.ts`）→ 改名/扩为 canonical packet 的装配器。
- 状态账本 `CharacterStateLedger` + `PendingStateDelta`（`src/lib/types.ts`、`character-states.ts`）→ 结算阶段的核心。
- 章末钩子、serialMode 连载条款、滚动排章 `outline_next`（`src/lib/volumes.ts`、prompts）→ 大纲工作区继续用。
- 分档模型（主力档 + `FINE_*` 精写档，`src/lib/ai.ts` 的 `FINE_WRITING_MODES`）→ 直接映射「规划任务走主力档、写章走精写档」。
- 章版本栈 `pushChapterVersion`（上限 12）→ 回滚机制的一半，另一半见第七节。
- 导出（`export-book.ts`：md/txt/epub/doc）、备份（`desktop-backup.ts`、`storage.ts` 自动备份）→ 原样保留。
- 一致性检查（`consistency.ts`）、本章体检（`chapter-health.ts`）、大纲↔正文对照（`outline_vs_content`）→ 併入审稿维度（第七节）。

### 1.3 为什么是退役而不是修补

1.6.0 的交互围绕「排好大纲 → 顺序生成」组织，作者的确认点（契约、定稿）是**串在生成动线上的关卡**，而不是**围绕资产的工作台**。需求要的是后者：资产（意图/人物/世界/大纲）有自己的家、有确认闸，写章是从资产出发的一次受控运行。在旧三段式上打补丁只会同时维护两套心智模型，故整体换壳、零件复用。

## 三、界面模仿说明（对照四张截图）

**总原则**：模仿的是**信息架构、层级与交互**；**不做像素级克隆**——不复制 OpenWrite 的字体、配色、圆角、图标与文案原句，不出现 OpenWrite/Goethe/Dante 名称，一律使用幻想作家现有主题变量（`globals.css` 的 `--bg-elevated`/`--border-soft` 等）与自有角色名。截图里的米黄纸感配色**不要**照搬——保留幻想作家现有明暗双主题。

| 截图 | 要模仿的 | 不要照抄的 |
|---|---|---|
| 1 总览 | 四张指标卡（正文字数/章节数/人物数/待处理伏笔）；全书进度条 + 目标字数；「创作资产 n/n 就绪」清单（逐项 就绪/缺失 圆点）；最近章节列表（章 id·字数·评分）；右栏助手常驻 | 「模型档案 · 2」徽标样式、「新手引导」按钮位置可自定；卡片阴影/字体 |

## 五、数据模型：正典 / 运行态分离与迁移

### 5.1 原则（对应 OpenWrite 的 src/ 与 data/）

OpenWrite 用目录物理分离：`src/`（人和 AI 共读的确认版真源）与 `data/`（正文、记忆、审稿、缓存、快照）。幻想作家的持久层是 IndexedDB 里单条 `project:{id}` JSON（`src/lib/storage.ts`），**不必改成文件目录**——做**逻辑分离**：`NovelProject` 顶层拆出 `canon` 与 `runtime` 两个分组，保存仍是一条记录、一次原子写（这恰好让「整章事务」实现更简单）。桌面端落盘备份（`desktop-backup.ts`）可选地把两组拆成 `src/`、`data/` 双目录镜像，P2 再说。

### 5.2 目标形态（schema v3 提案，字段名供参考，实施者可调）

```text
NovelProject (schemaVersion: 3)
├── canon                       # 确认版真源；只能经 diff 闸写入
│   ├── authorIntent            # 作者意图：premise/theme/endingDirection/coreConflict/forbidList
│   │                           #   ← 迁自 PremiseCard；「仅作者不进提示词」标记保留原语义
│   ├── currentFocus            # 创作罗盘：近期阶段目标/必须保留/必须避免（新增）
│   ├── foundation              # 故事基础 ← StoryBackground
│   ├── characters[]            # ← Character（真相层 truth 仍仅作者）；新增 confirmed 态
│   ├── world[]                 # ← LoreEntry；锁定事实 LockedCanonFact 并入（locked 标记保留）
│   ├── outlineTree             # 卷→幕→节→章 四级树（新）；章节点承载 OutlineChapter 全部字段
│   └── threads[]               # ← PlotThread 伏笔/线索板（作者确认口径）
├── runtime                     # 运行态；管线与结算写入，作者一般不手维护
│   ├── manuscript[]            # ← ChapterContent（正文、versions、scenes、canonWarnings）
│   ├── memory[]                # 章摘要/touchedThreads/账本 CharacterStateLedger/AccountRepairMark
│   ├── reviews[]               # 审稿记录：每章问题清单、维度、严重度、评分、复审对比（新）
│   ├── sessions[]              # AI 协作会话（P1）
│   ├── runs[]                  # 写章运行记录：阶段、耗时、错误、写前快照引用（新）
│   ├── jobs                    # ← BookGenerationJob
│   └── drafts[]                # 规划 Agent 的未确认提案（大纲草稿等）；确认后才进 canon（新）
├── settings                    # GenerationSettings + 全书/分卷字数目标（新增 wordTargets）
└── id/name/tags/original/…     # 顶层元数据不动；original 旧稿归「项目迁移」语义
```

要点：

- **草稿非正典**：`outline_draft` 类产物一律进 `runtime.drafts`，对应 OpenWrite 的「`outline_draft.md` 不是第二份大纲」FAQ。大纲工作区只渲染 `canon.outlineTree`。
- **树的兼容**：`OutlineChapter.order` 全书连续序保留（记忆包、`outline_next`、导出都依赖它），树只是分组视图的持久化；幕/节允许为空标题的「默认组」。
- **摘要与账本从 `ChapterContent` 挪到 `runtime.memory`** 是逻辑归位，实施者若评估改动面过大，可以先保留字段位置、只在类型层与选择器层建立 canon/runtime 视图——**分离的强制点是「写入路径」而非「字段住址」**。

### 5.3 旧项目迁移（v2 → v3）

- 入口沿用 `normalizeProject`（`src/lib/types.ts`）的版本递增惯例；迁移前按 `storage.ts` 既有 `migration-backup-*` 模式先落 IDB 备份，失败可整体还原。
- 映射：`premise`→`canon.authorIntent`；`background`→`canon.foundation`；`characters`→`canon.characters`（全部标记 `confirmed: true`，既有数据视为作者已确认）；`lore` + `canon`（LockedCanonFact）→`canon.world`；`volumes` + `outline.chapters`→`canon.outlineTree`（每卷自动包一层「第一幕/第一节」默认组，章序不变）；`plotThreads`→`canon.threads`；`chapters`→`runtime.manuscript`；`characterStates`/摘要→`runtime.memory`；`bookJob`→`runtime.jobs`；`lastConsistencyReport`→`runtime.reviews` 的首条历史记录。
- `currentFocus` 初始化：取当前卷的 `arcGoal`/`exitState` 拼一段占位文案，标注「迁移生成，请修改」。
- `reviewState: "reviewed"` 的旧章在新审稿工作区显示为「已审（旧流程）」，不伪造维度化审稿记录。
- 迁移必须**无损可逆**：导出 JSON（`exportProjectJson`）在 v3 下继续可导入；v2 JSON 导入时走同一迁移函数。补单测：v2 全量样例 → 迁移 → 断言章序/正文/账本逐字不变。

## 六、双 Agent 分工：规划与写作

### 6.1 命名

保留 OpenWrite 的「规划 / 写作」双角色拆分（这是硬需求），命名本地化：

- **规划 Agent：「织卷」** —— 把灵感织成可写的卷册资产（意图、人物、世界、大纲）。
- **写作 Agent：「落墨」** —— 落笔成文，负责写章、审稿、修订与结算。

理由：Goethe/Dante 取自西方文豪，对中文网文作者无直觉；「织卷/落墨」是功能自明的中文双字名，且都不与既有商标冲突。UI 中始终以「规划 · 织卷」「写作 · 落墨」双标签出现，避免只记名字不知分工。名字是作者一句话能改的常量（集中放 `src/lib/brand.ts`），不因命名争议阻塞实施。

### 6.2 职责与边界

| | 织卷（规划） | 落墨（写作） |
|---|---|---|
| 读 | 全部 canon + 会话内素材 | canon + packet（有界） |
| 写 | **只能提案**：对 canon 的每次写入生成结构化提案（新增/修改/删除 + 字段级前后值），经 diff 闸作者确认后才落 canon | **只能写 runtime**：正文、摘要、账本增量、审稿记录；对 canon 零直接写权。若写作中发现设定矛盾，产出「正典疑议」条目挂到审稿问题清单，由作者转给织卷处理 |
| 模型档 | 主力档（DeepSeek，量大价低） | 正文/修订走精写档（`FINE_*`，已有分流表），摘要/审稿走主力档 |
| 任务映射（现有 `GenerateTaskMode`） | `outline`、`outline_volume`、`outline_next`、`polish_chapter_outline`、`expand/optimize character|background|cast`、`extract_canon`、`extract_skeleton` | `chapter`、`continue`、`rewrite`、`scene_plan`、`scene_chapter`、`chapter_summary`、`consistency_check`、`outline_vs_content` + 新增 `review_chapter`、`revise_propose` |

### 6.3 作者必须确认的点（闸门清单）

1. **正典 diff 闸**（P0）：织卷的每份提案渲染为字段级 diff（旧值/新值并排，中文标签），按钮只有「确认写入 / 放弃 / 编辑后写入」。确认动作不可由旧会话、模型口头宣称替代——这条直接抄 OpenWrite 的语义。
2. **写前指导**（P0）：「写下一章」弹出的对话框展示本章大纲节点 + 可编辑的本章指导（goal/hook/字数目标，预填自 `OutlineChapter`），作者点「开始写」才进管线。
3. **修订提案闸**（P1）：审稿问题的「生成修订提案」产出正文 diff，作者确认才应用（应用前自动 `pushChapterVersion`）。
4. **结算摘要**（P0，轻确认）：结算完成后在正文页展示「本章入账：状态 n 条、伏笔触及 n 条、摘要已存」，提供一键撤销（用写前快照回滚），不强制逐条点收——账本增量沿用现有 `pendingStateDeltas` 的可改可弃交互。

## 七、写章管线契约

### 7.1 阶段

```text
[写前检查 precheck] → [组装 packet] → [初稿 draft] → [审稿 review]
→ [修订 revise（可选，循环）] → [状态结算 settle] → [提交 commit / 失败回滚 rollback]
```

每次运行落一条 `runtime.runs[]` 记录：阶段、起止、模型档、token/字数、错误、快照引用。运行期间持**项目级写锁**（同一项目同时只允许一个写章运行；与 `bookJob` 互斥——批量队列内部也是逐章走此管线）。

1. **precheck（P0）**：模型已配置（`/api/config` 诊断）；目标章在 `canon.outlineTree` 中存在且为待写；canon 就绪度（意图/人物/大纲非空，缺项给黄色警告但不硬阻断——旧稿迁入的书可能没有完整资产）；无未完成的运行/残留锁；存储可写。失败 → 弹原因，不进入下一阶段。
2. **packet（P0）**：升级 `buildMemoryPack` + `chapter-contract` 为单一装配器，产出结构化 packet：作者意图（可注入部分）+ 创作罗盘 + 滚动大纲窗（本卷 + 本章前后各 2 章节点）+ 最近 2 章正文尾部 + 近 5 章摘要 + 出场人物卡（账本最新状态行优先）+ 命中 world 条目 + 开放伏笔 ≤12 + 上章钩子 + 本章指导。**有界是契约**：不整书注入（`injectFullOutline` 默认关的现状保持）。packet 可在助手栏「上下文」页签 dry-run 预览。
3. **draft（P0）**：走精写档流式生成（现 `streamGenerate(mode:"chapter")`），字数不足自动补足（现 continue 逻辑），全部发生在事务内。
4. **review（P0）**：主力档跑 `review_chapter`，输出结构化 JSON：`issues: [{dimension, severity: high|medium|low, title, evidence(原文短引), suggestion, locatable}]` + 总分。**首发 10 维**：① 承接上章钩子 ② 章末钩子落点 ③ 大纲符合度（收编 `outline_vs_content`）④ 人物状态连续性（称呼/伤势/位置，对账本核）⑤ 人物动机可信 ⑥ 世界设定一致（对 world/locked facts 核，收编 canonWarnings）⑦ 禁写清单违规 ⑧ 节奏与信息密度 ⑨ 视角与人称 ⑩ 语言重复/口头禅。维度表做成数据驱动的 registry，加维度=加一条配置+提示词段，这是通往「加厚到 20+/37」的路。评分 = 100 − 加权扣分，权重在 registry 里，不神化。
5. **revise（P1）**：对 `locatable` 的问题生成修订提案 diff；作者逐条确认应用。P0 阶段作者可直接在编辑器手改后「重跑审稿」。
6. **settle（P0）**：一次主力档调用（现 `chapter_summary` 扩展）产出：散文摘要 + `pendingStateDeltas` + 伏笔触及；写入 `runtime.memory`（账本入账沿用 `character-states.ts` 的合并与 KEEP=6 规则）、更新伏笔 touched、大纲树该章标已写、`reviewState` 按审稿结果置初值。
7. **commit / rollback（P0）**：正文 + 摘要 + 账本增量 + 伏笔状态 + 树节点状态**作为一个提交单元**一次 `upsertProject` 落库。进入 draft 前先做**写前快照**（章正文版本压栈 + 账本/伏笔/树节点状态的浅拷贝存入 run 记录）；draft/settle 任一步失败或作者中止 → 用快照整体还原，项目回到写前状态。

### 7.2 失败模式与处置

| 失败 | 处置 |
|---|---|
| 模型 4xx/超时（精写中转不稳是已知现实） | draft 阶段：保留已流出的 partial 为「草稿（未提交）」，作者可选重试（重试=新 run，复用同 packet）或放弃回滚；settle 阶段：正文保留，标记「结算未完成」，提供单独重跑结算按钮，**不**因摘要失败丢正文（沿用 `summaryFailed` 的既有取舍） |
| 审稿/结算 JSON 解析失败 | 容错解析（沿用 `parseTouchedThreads` 的宽松套路）；完全不可解析 → 该阶段标 failed，正文不回滚，审稿可单独重跑 |
| 应用中途崩溃/强退 | 重开项目时检测 `runs[]` 中 status=running 的残留 → 弹「上次写章未完成」：还原快照 / 保留现状清除锁。锁必须是数据里的字段而非仅内存态 |
| 字数严重不足且补足两轮仍不足 | 停止自动补足，标记问题进审稿清单（维度⑧），不无限烧钱 |
| canon 违规（焕新锁定事实） | 沿用 `evaluateRenewalSave` 语义：警告 + 需作者显式 force，纳入审稿维度⑥ |
| 存储写入失败（配额/IDB 异常） | commit 前置检查 + 失败时不清快照，弹导出 JSON 逃生口（`exportProjectJson` 现成） |

## 八、本迭代明确不抄的部分

1. **Python Studio 本体 / 任何形式的 Python sidecar**——契约在 Next.js API 路由 + `src/lib` 中重表达，硬约束。

4. **LightRAG / FastEmbed 本地向量与图谱检索**——见第四节 P2 行；本迭代的「不漂移」由账本 + 有界 packet + 审稿承担。

6. **Vditor 编辑器与 OpenWrite 全部 UI 资源/文案/名称**——许可与商标边界；编辑器引擎升级另立项。
7. **127.0.0.1 Web 服务对外形态**——我们本来就是 Electron 壳内嵌 standalone server，不改变进程模型。

## 十、风险

- **R1 首启输入冻结复发（历史包袱，最高优先）**：1.5.1 修过首页首键冻结（`home-boot.ts`、`schedule-idle.ts`：首帧不 disable 输入、IDB 延后、静默更新延迟 20s、不扫大目录）。新壳更重（左导航 + 总览多卡 + 助手栏），**必须**沿用同一纪律：工作区惰性挂载、总览数据延后一拍、迁移（v2→v3 normalize）绝不放在首帧同步跑。S2 验收含首启键入实测。
- **R2 Electron 窗口与三栏布局**：1480×960 默认窗（`electron/main.cjs`）下「左导航 + 主体 + 助手栏」可能挤压编辑器。定收起策略（助手栏可折叠、左导航可窄化为图标）并设最小宽断点；不改窗口默认值以外的打包配置。
- **R3 MIT 洁净**：只学结构不搬代码/资源/文案；S8 落致谢；评审时 diff 里出现任何 OpenWrite 源片段即打回。
- **R4 用户数据迁移**：v3 是本仓最大一次 schema 变更。迁移备份 + 可逆导出 + v2 导入兼容三重保险（5.3 节）；灰度上建议 S1 合入后先发一个内部验证版本再继续 S2+。
- **R5 成本与延迟**：新管线每章固定多两次主力档调用（审稿 + 结算）。结算合并进现有摘要调用（同一次输出），审稿提供「跳过本次审稿」开关，给作者省钱路径。
- **R6 范围失控（单人维护现实）**：37 维、语义检索、参考库、编辑器引擎全部后置且在第八节点名；任何切片若发现要动第八节清单里的东西，先停下改计划而不是顺手做。
- **R7 审稿质量落差**：10 维靠提示词 + 账本/大纲对照，达不到 OpenWrite 成熟度是预期内的；用 registry 数据驱动保证「变厚」不用重构，且审稿结果永远是建议而非自动改稿（修订必经闸）。
