## 〇、一段话结论

六条文案/布局修正（R1–R5、R7）都只动 `packages/studio/src` 的文案表、侧栏系统区顺序、`AuthorPage` 的书目区、首页封面卡三处，各是几行到几十行的删改。R6 **不是路由或状态问题**：点侧栏会话、点进程条「问心」、直开 `#/book/:id/chat` 三条路径下抽屉都已经渲染出来了（`data-testid="book-talk-drawer"` 存在，420px 宽）；真正的问题是抽屉里**同时塞了 `ChatPage` 和 `BookSidebar`**，而 `BookSidebar` 是为旧的整页对谈布局写的（宽度 = 窗口 40%，最小 280、最大 700，`shrink-0`，`lg:` 以上必显示），在 420px 抽屉里它把 `ChatPage` 挤到 **0px**，用户只看见「下一章 / 章节 / 核心文件」那块书籍信息面板——看起来就是「还是书房界面」。修法是把 `BookSidebar` / `BookSidebarToggle` 从抽屉里拿掉（已在本地验证：`ChatPage` 恢复到 419px，输入框、空态、快捷动作、「重新推敲前提」芯片全部可见），再顺手把关闭抽屉时残留的 `/chat` hash 清掉。建议合成**一个小 PR**（`P0-4 首页侧栏抛光与问心抽屉修复`），不 bump。

### D.1 复现（v2.1.1 生产构建，headless Chrome，窗口 1480×960 = Electron 默认尺寸）

### D.2 根因

1. **不是路由、不是状态、不是会话加载**：三条入口都正确把 `bookChatOpen` 置 true，`#/book/:id/ask` 与 `/chat` 别名解析正确，`Sidebar.openSession` 的 `activateSession → toBookChat → loadSessionDetail` 顺序与 `ChatPage` 挂载 effect（L532–646：先 `loadSessionList(bookId)`，若当前活动会话属于本书就直接 `loadSessionDetail`）配合正常。
2. **是布局**：`App.tsx` L444–455 把 `ChatPage` + `BookSidebar` + `BookSidebarToggle` 三个组件放进 420px 抽屉的一个 `flex` 行。`BookSidebar` 是 `shrink-0` 且宽度按窗口 40%（280–700px）计算，在 ≥1024px 视口下必渲染；它先吃满 420px 并溢出，`ChatPage`（`flex-1 min-w-0`）被压到 0。
3. **为什么现在才暴露**：P0（#93，v2.1.0）把 pre-P0 的整页 `#/book/:id/chat` 布局原样搬进抽屉时就已如此，但当时进程条「问心」跳独立的 `BookAskPage`（只读故事卡）、聊天靠「对谈」按钮开抽屉，用户对「对谈」抽屉的期待没那么高；#98 删掉「对谈」按钮和 `BookAskPage`、把「问心」= 开抽屉后，抽屉成了**唯一**聊天入口，问题才被当成「问心不出现」报上来。
4. `BookSidebar` 面板内容（下一章预检 / 章节 / 核心文件）与书房页高度重合，用户看到它自然认为「还是书房界面」。

### D.3 修复步骤（一个 PR 内完成）

**D3-1 主修（必做）** — `App.tsx` 抽屉块：删除 `<BookSidebar …/>` 与 `<BookSidebarToggle …/>` 两行及其 import（若 App 中无其他引用）。`ChatPage` 独占抽屉宽度。本地验证结果：`ChatPage` 根节点 419px；空态「告诉我你想写什么——题材、世界观、主角、核心冲突」、快捷动作条（`overflow-x-auto`，可横滑）、「重新推敲前提」芯片、输入框（243px）与发送按钮全部可见可点。
