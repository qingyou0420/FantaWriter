# 2.0 P1 硬闸复审（PR #53 · `cursor/inkos-p1-hard-gates-4d56`）

> 复审对象：PR #53「feat: InkOS P1 hard gates (G1–G6, hook overdue)」，commit `22c9e53`，对照 `docs/2.0重构蓝图-InkOS内核桌面重建方案.md` §3 / §6（G1–G6）/ §9-P1 与 owner 规则（不得回潮 1.x FantaWriter UI）。
> 方法：全量 diff 逐文件读码 + 绕过路径狩猎（重点查"闸只在一处、旁边还有能写的路"）+ 本机跑 `pnpm test` / `pnpm build` / `pnpm engine:smoke` / `pnpm test:core:full`（并与 master 基线对照）。

## 结论：**merge after blockers**（两项阻断修掉即可合，见 B1/B2）

PR 声明的六道闸与钩子逾期**主体是真闸不是标签**：G1/G5 在服务端与管线层双重拒绝，G3 提案落盘且带 revision 校验，G2 packet 落盘，G6 违规进 critical 链路。P0（PR #50）锁/中止无回归。没有 1.x UI 回潮。但 G3 存在一条整面墙级别的绕过（B1），且 G1 闸击穿了上游全量测试套件约 37 个用例（B2，被本环境的 fts5 缺失恰好掩盖）。

## 一、阻断项（必须修）

### B1 · G3 绕过：Chat 可经 `sub_agent(architect, revise)` 整体重写 foundation，无 diff 无确认

- 书内 Chat 会话的工具集无条件包含 `sub_agent`（`packages/core/src/agent/agent-session.ts` `bookTools`，约 972 行起）。
- `sub_agent` 的 architect 分支带 `revise: true` 时直接调 `pipeline.reviseFoundation(bookId, feedback)`（`packages/core/src/agent/agent-tools.ts` 约 981–999 行），**执行前没有任何 propose_action / staged diff / 确认按钮**（`prepareSubAgentArguments` 只做 platform 归一化）。
- `reviseFoundation`（`packages/core/src/pipeline/runner.ts:884`）让 Architect 重新生成并**直写** `story_frame` / `volume_map` / `roles/*` / `book_rules`（旧稿备份到 `story/.backup-phase*-<ts>/`，但备份不是人闸）。
- 后果：G3 把 `write_truth_file` 关严了，但 agent 想"顺手"重写整个正典骨架时走这条路一样能写。蓝图 §6-G3 的定义是"Agent 对 direction/foundation/rules 的**一切写入**必须经 staged diff + UI 按钮确认"、§6 总则"代码路径上不存在绕过分支"——这条路径直接违反。这正是狩猎清单里的"other agent still writing foundation files without confirm"。
- 修法（三选一，工作量都不大）：
  1. 书会话工具集里禁掉 architect `revise` 分支（建书会话不受影响，那条本来就走 confirmed `propose_action`）；
  2. `reviseFoundation` 的输出改为逐文件 `stageTruthProposal`，复用现成确认卡；
  3. `sub_agent(architect, revise)` 要求 confirmed action payload（与 `createBook`/`writeNext` 同款 `isConfirmedProductionAction` 机制）。

### B2 · G1 闸击穿上游全量测试套件（约 37 个用例，被本环境掩盖）

- `pnpm test`（CI 跑的精选子集，`.github/workflows/test.yml`）**绿**，PR 声明属实。
- 但 `pnpm test:core:full` 下，约 **37 个上游用例**（`pipeline-runner.test.ts`、`chapter-analyzer.test.ts`、`composer.test.ts`、`chapter-batch.test.ts`、`planner.test.ts` 等）现在在 `prepareWriteInput` 处被 G1 掷出 `WritePreflightError`（夹具没有 volume_map 条目 / story_frame / author_intent），例如：
  - `PipelineRunner > routes writeDraft through planner and composer on the governed path → author_intent.md is empty or still a placeholder.`
- 本环境对照结果有欺骗性：master 与 PR 分支**同为 117 个失败且失败集合完全一致**——因为本机 `node:sqlite` 缺 fts5，这些用例在 master 上本来就因环境挂。但 G1 失败发生在任何 sqlite 调用**之前**，是确定性的、与环境无关的；在 fts5 正常的开发机上，这 37 个将是 PR 的**新增失败**。
- 修法：夹具补三件套（一行 volume_map 条目 + 非空 story_frame / author_intent），或给测试路径注入显式的 gate 旁路选项。机械改动，不影响产品语义。

## 二、逐闸复核（对照 PR 声明）

### G1 · 写前闸 —— 属实，是硬闸

- `evaluateWritePreflight` / `WritePreflightError(code: WRITE_PREFLIGHT)`（`packages/core/src/pipeline/write-preflight.ts`）：无 volume_map 条目、story_frame / author_intent 空或占位、上一章未 settled（`approved|published|imported`）四类结构化原因，`skipPreviousApproval`（带病续写）**只**豁免上一章一条。
- **无 first-directive 兜底**：`packages/core/src/utils/volume-map-entry.ts` 只认"第 N 章 / Chapter N"精确行与含 N 的闭区间范围行，文件头注释明说不用 planner 的 first-directive 回退。核对属实。
- 双重执行点：Studio `POST /write-next`、`POST /draft` 路由层同步评估（409 + `details.reasons`），且 `PipelineRunner.prepareWriteInput` 内 `enforceWriteGate: true` 再执行一次（`runner.ts:1196`、`:2133`、`:3418`）——Chat `sub_agent(writer)`、CLI `inkos write` 等一切进管线的写章路径都被兜住。**不是 UI-only**。
- `throwIfBookBusy` 在 G1 之前（server.ts write-next/draft 路由），BOOK_BUSY 仍先报持锁者——与 PR 声明一致，P0 语义未变。
- G1 失败发生在 `taskId` 注册与取锁**之前**，不留半状态。
- UI：BookDetail 落墨/草稿按钮按 preflight 禁用并给结构化原因 + 跳转排纲/审稿（`SerialCockpitStrip.tsx`）；UI 侧 `.catch(() => setPreflightOk(true))` fail-open 无妨——服务端硬闸兜底。
- 边界备注（非阻断）：`writeChapters` 批量写 N 章时第 2..N 章自动置 `skipPreviousApproval`（`runner.ts` 约 1966 行）——批写语义下合理（批内前章不可能已 approve），volume_map/骨架检查仍逐章执行；建议文档化。

### G2 · packet 快照 —— 属实

- `writeGovernedRuntimeArtifacts` 每次治理组包**必写** `story/runtime/chapter-NNNN.packet.json`（`packages/core/src/utils/runtime-writer.ts` + `utils/packet-snapshot.ts`），含 contextPackage / ruleStack / trace / 逐源 protected·compressed 标记与 token 预算。落盘即验收，符合蓝图 §3.5"改造点很小"的口径。

- 小瑕疵：`PacketSourceRecord.truncated` 硬编码 `false`；`estimateTextTokens` 本地重复实现（len/2）。不影响验收。

### G3 · 正典 diff 人闸 —— 主闸真，但见 B1 与 S1

- `write_truth_file` 对 direction/foundation/rules（`classifyTruthAuthority` 已补 `story_frame`/`volume_map`/`outline/*`/`roles/*`）**只暂存不写**（`agent/agent-tools.ts:3332` 起），提案落 `story/runtime/proposals/<uuid>.json`（`interaction/truth-proposals.ts`），返回 `kind: "proposed_truth_diff"`。

- **刷新不丢**：提案在 stage 时即落盘，磁盘为唯一事实源；`GET /truth-proposals?status=pending` 可枚举。狩猎项"Proposal loss on refresh"未命中。

## 三、应修不阻断（按优先级）

- **S1 · G3 闸位偏离蓝图锚点**：闸装在 `write_truth_file` 工具包装层，而蓝图 §6-G3 锚点是 `interaction/project-tools.ts` 写入口。后果是 `interaction/runtime.ts` 的 `edit_truth` 意图（case 约 955 行）仍直呼 `tools.writeTruthFile` 直写正典——当前 Studio 只用该 runtime 跑 `create_book`/`export_book`（server.ts:2973/5823），CLI TUI 只剩显示标签，属"exported 但未接线"的绕过分支。建议闸下沉到 `project-tools.writeTruthFile`（runtime-truth 例外放行）或删掉 `edit_truth` case，一劳永逸。
- **S2 · G5 同样只在路由层**：CLI `inkos review approve` / `approve-all`（`packages/cli/src/commands/review.ts:127,165`）直改 status，无 `assertChapterApprovable`。桌面产品面未暴露 CLI，但按"代码路径无绕过分支"应把闸下沉到共享层（如 StateManager 级 approve helper）。
- **S3 · `audit-failed` 无 critical 时可 approve**：approve 路由只看 critical 集合，不看章状态。若审计因纯分数不过线而 fail（无 critical issue），G6"audit-failed 不得 approve"落空。`assertChapterApprovable` 加一条 status 检查即可。
- **S4 · `rename_entity`**（`agent-tools.ts:3388`）跨 truth 文件（含 `roles/*`）机械改名，无确认。确定性替换、漂移风险低，可接受但应在文档里显式豁免或补确认。
- **S5 · G6 与 G5 override 的语义混合**：craft 违规产生的 critical 可被显式 override 放行；蓝图 G6 写"不得 approve"。override 有留痕，倾向可接受，但需 owner 拍板 intended 与否。

## 四、次要备注

- M1 · `ChatPage.handleConfirmTruthDiff` 先 `markProposalResolved("confirmed")` 再 await apply——`TRUTH_REVISION_CONFLICT` 时卡片显示「已写入」而文件未写（服务端安全，UI 误导），应在 catch 里回滚卡片状态。
- M2 · 新增 GET 路由（write-preflight / review-queue / packet / hooks/due / truth-proposals）未过 `isSafeBookId`，`StateManager.bookDir` 是裸 join。与既有 GET 路由一致、loopback-only，加固项。
- M3 · truth-proposal apply 落盘走路由内裸 `writeFile`（在书锁内），未复用 `project-tools.writeTruthFile` 的清洗/记录逻辑；apply 时也未对 `staged.fileName` 复跑 `assertSafeTruthFileName`（stage 侧已校验，提案文件在书目录内，威胁模型可接受）。
- M4 · packet 快照 `truncated: false` 硬编码、token 估算重复实现（见 G2）。
