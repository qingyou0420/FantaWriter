# 幻想作家 2.0 重构蓝图：以 InkOS 为内核的 Windows 桌面连载工作台

> **本文性质：仅规划，不含任何实现。** 不改业务代码、不动版本号。
> 面向作者本人（流离羽）与后续实施 Agent。目标：让一个人类作者在 AI 辅助下**连载数月**的中文网文长篇，质量稳定、剧情人物不漂移——**人类掌握骨架与灵魂**（大纲、人物、世界观、结局方向），**AI 在轨道上写章**。
>
> 研究方法：三仓库实读（2026-09-01 核实）——本仓 master（v1.7.1）、[InkOS](https://github.com/Narcooo/inkos)（v1.8.0，AGPL-3.0，TypeScript pnpm monorepo）、[OpenWrite](https://github.com/LiPu-jpg/Openwrite)（v5.8.0，Apache-2.0，Python）。所有断言均给出文件/模块锚点；**未实际运行 InkOS Studio 与 OpenWrite Studio 的 GUI**，凡属推断处标注「猜测，需实施者验证」。
>
> 作者已接受：新幻想作家因基于 InkOS 而采用 **AGPL-3.0**。

---

## 〇、一段话结论

**放弃「继续在 Next.js 里模仿别人」的路线，改为：fork InkOS 全仓作为新幻想作家的内核与工作台，用现有 Electron 壳的桌面基建（单实例、钉端口、自动更新、密钥隔离、安装包）把它包成真正的 Windows 桌面应用；在 fork 里修掉 InkOS 的四个桌面性硬伤（进程内锁不可恢复、项目根依赖 CWD、无单实例语义、truth 写入绕锁），再把 OpenWrite 里真正防漂移的四道闸（大纲范围确认、正典 diff 人闸、审稿问题队列、伏笔逾期账本）移植到 InkOS 原语上。** 理由：研究证实 OpenWrite 引以为傲的 37 维审查本身就是从 InkOS 移植的（InkOS `continuity.ts` 33 个基础维度 + `fanfic-dimensions.ts` 34–37），InkOS 的管线（架构师→规划→写作→观察→结算→连续性审计→修订→状态校验）、正典/运行态分离、原子文件集提交、逐章快照，已经覆盖了幻想作家 1.4–1.7 三轮迭代想造而没造好的几乎全部东西；缺的只是**桌面**和**几道人闸**。作者说「网页版 InkOS 比幻想作家好用，但网页 UX 仍不是日常写作想要的」——那就把引擎连 UI 一起拿来，装进桌面壳，然后按 1.7 大纲工作区复盘（`docs/1.7大纲工作区OpenWrite对照与整改方向.md`）已经付过学费的教训去改它的工作台，而不是第三次从零仿造。

## 一、三方深度对照

### 1.1 总览表

| 维度 | InkOS 1.8.0 | OpenWrite 5.8.0 | 幻想作家 1.7.1 |
|---|---|---|---|
| 语言/形态 | TypeScript，pnpm monorepo（`packages/core`+`cli`+`studio`），Node ≥22 | Python，`tools/` 单包 + stdlib HTTP Studio | Electron 37 + Next.js 16 standalone + React 19 |
| 许可证 | AGPL-3.0-only | Apache-2.0 | MIT |
| 数据落地 | **本地文件**（Markdown+JSON+SQLite），`books/<id>/` | **本地文件**（Markdown+YAML），`data/novels/<id>/` | **浏览器 IndexedDB**（`fantawriter` 库，`project:<uuid>` 键） |
| 正典/运行态分离 | 有，代码级（`truth-authority.ts` 五类权威） | 有，目录级（`src/` 确认正典 vs `data/` 运行态） | 弱（`canon`/`canonDrafts` 字段级，无目录概念） |
| 写章管线 | 规划→组包→写作→观察→结算→审计→修订→校验→原子落盘→人批 | preflight→组包→初稿→事实提取→结算→校验→提交（Run V2 阶段机） | precheck→draft→review→settle→commit（`write-pipeline.ts`） |
| 审查 | 33+4 维连续性审计（`continuity.ts`+`fanfic-dimensions.ts`）+ 确定性 post-write | 37 维（**自述"从 InkOS 融合"**，`reviewer.py DIMENSION_MAP`）+ 修订提案人批 | 单次 `review_chapter` 提示词审查 |
| 锁 | 进程内 Map + 心跳租约锁文件（`.write.lock`），跨进程可自愈、**进程内不可自愈** | `ProjectWriteLock`（写事务级） | `writeRuns` 软锁（precheck 拦截陈旧 run） |
| 桌面性 | 无。CLI 起 Web Studio，根=CWD，端口 4567，无单实例 | 无。`127.0.0.1:4567` stdlib HTTP，`.bat` 启动 | **有**：单实例、钉端口、NSIS 安装包、自动更新、密钥文件隔离 |
| 模型配置 | OpenAI 兼容 custom base URL 一等公民 + 按 Agent 角色 `modelOverrides` | LiteLLM + `model_profiles.py` 八条路由 | `DEEPSEEK_*` 主槽 + `FINE_*` 精修槽 |

### 1.2 架构

**InkOS**：内核 `@actalk/inkos-core`（`packages/core/src/index.ts` 导出 `StateManager`、`PipelineRunner`、全部 Agent、`createLLMClient`、运行态 Zod schema 等）与表现层干净分离；`packages/cli`（bin `inkos`）直接进程内调用 core，证明**不经 HTTP 也能驱动全部能力**；`packages/studio` 是 Hono HTTP API（100+ 路由，SSE `/api/v1/events`）+ Vite/React 19/Zustand SPA，托管在同一 Node 进程。Agent 执行层基于 pi-agent（`@mariozechner/pi-agent-core` 0.67.1），带中止传播（CHANGELOG v1.7.0）。

**OpenWrite**：`tools/` 下约 90 个 Python 模块；Studio 是 `tools/studio_application.py` 的 stdlib `ThreadingHTTPServer`（`create_server(..., host="127.0.0.1", port=4567)`）+ `tools/studio_assets/` 静态 SPA（原生 JS + Vditor）。业务与 HTTP 耦合较松（`StudioApplication` 委托 `NovelApplicationService`/管线），但整个运行时是 Python——**按既定非目标，不嵌入、不移植其运行时**。

**幻想作家**：`electron/main.cjs` 以 `ELECTRON_RUN_AS_NODE=1` 方式拉起 Next standalone `server.js`（loopback、钉端口），渲染层是一个巨型 `src/app/project/[id]/page.tsx` 编排器 + IndexedDB 存储（`src/lib/storage.ts`）。业务逻辑（组包、管线、闸）散在 `src/lib/*` 与 React 状态之间，**数据在浏览器存储而非用户可见的文件**——这是与前两者最根本的差别，也是迁移故事的核心难点。

### 1.3 数据模型：正典 vs 运行态

**InkOS 书目录**（`StateManager.bookDir` = `<项目根>/books/<bookId>/`，布局由 `agents/architect.ts` 写就、`isCompleteBookDirectory` 校验）：

```text
books/<bookId>/
  book.json                      # 书配置（models/book.ts BookConfigSchema）
  .write.lock                    # 心跳租约锁文件
  chapters/NNNN_标题.md          # 正文（含 .versions/ 与 .trash/）
  chapters/index.json            # 章节索引（ChapterMeta[]）
  story/
    outline/story_frame.md       # 主题/世界/结局方向（正典基础）
    outline/volume_map.md        # 逐卷 OKR + 章级规划（正典基础）
    roles/主要角色|次要角色/*.md  # 人物卡（正典）
    book_rules.md                # 可执行规则卡（正典，禁令载体）
    author_intent.md             # 作者意图（方向类正典）
    current_focus.md             # 近期焦点（方向类正典）
    current_state.md             # 运行态真相投影（人读）
    pending_hooks.md             # 钩子/伏笔账本投影（人读）
    chapter_summaries.md         # 记忆投影（人读）
    state/*.json                 # 结构化运行态真相（Zod 校验，机器权威）
    snapshots/<n>/               # 逐章快照（回滚用）
    runtime/chapter-NNNN.*       # 章计划、trace、run.json
    memory.db                    # SQLite FTS 叙事记忆（node:sqlite）
```

权威分类在代码里是显式的：`packages/core/src/interaction/truth-authority.ts` `classifyTruthAuthority()` 把 truth 文件分为 direction（intent/focus）、foundation（大纲）、rules、runtime-truth（current_state/hooks）、memory 五类。Agent 只能写允许清单内的文件（`interaction/project-tools.ts` `assertSafeTruthFileName`）。

**OpenWrite**：`src/outline.md` 是**唯一大纲语义真源**（根 `SKILL.md` 明文），`models/outline.py` 四级树（MASTER/ARC/SECTION/CHAPTER，章节点带 goals/beats/hooks/involved_characters/estimated_words/emotional_arc 元数据），写入受 `tools/outline_contract.py` `validate_outline_markdown()` 契约校验；运行态真相在 `data/world/`（`current_state.md`/`ledger.md`/`relationships.md`，`tools/truth_manager.py TruthFilesManager`），伏笔在 `data/foreshadowing/dag.yaml`。**确认过的 `src/**` 与派生的 `data/**` 目录级分离**。

**幻想作家**：单个 `NovelProject` JSON（`src/lib/types.ts`，schemaVersion 3）装下一切——`outline.chapters`（扁平章数组，真源）、`outlineTree`（卷→幕→节→章分组视图）、`characters`、`premiseCard`（含作者私有的 theme/endingDirection）、`canon`（锁定事实）、`plotThreads`、`characterStates` 账本、`chapters[]` 正文。数据层设计其实健康（1.7 复盘原话），但存在 IndexedDB 里，作者无法用文件管理器/Git/外部编辑器触达。

### 1.4 写作管线

**InkOS**（`packages/core/src/pipeline/runner.ts`，全程持书锁）：
1. `prepareWriteInput` → `PlannerAgent` 章意图/备忘 + `ComposerAgent` 治理式组包（选大纲节、记忆、引用）；
2. `WriterAgent.writeChapter`（`agents/writer.ts`）三段：创作正文 → Observer 观察（`observer-prompts.ts`）→ Settler 结算（`settler-prompts.ts`，产出运行态 delta：current_state 补丁、钩子操作、章摘要）；
3. 审查环（`pipeline/chapter-review-cycle.ts`）：`ContinuityAuditor.auditChapter`（编号维度审计）→ `ReviserAgent` 按 `revisionGate`（strict/lenient/always）修订 → 确定性 post-write 检查（`post-write-validator.ts`：章号引用、AI 痕迹等）+ 钩子账本检查；
4. `StateValidatorAgent` 校验结算 → `commitAtomicFileSet`（`utils/atomic-file-set.ts`）**原子写入** 章文 + Markdown 投影 + `story/state/*.json`，并落 `story/snapshots/<n>/`；
5. 章状态 `ready-for-review` | `audit-failed` | `state-degraded`，**人批** `POST /api/v1/books/:id/chapters/:num/approve` 或 CLI `inkos review approve` 才算定稿。

**OpenWrite**（`tools/chapter_pipeline.py` `execute_write_chapter`）：`ProjectWriteLock` 包全程；写前 `truth_manager.create_snapshot`；成功则一次性提交 章文（`_atomic_write`）+ 运行态 delta + 章记忆（`ChapterMemoryStore`）；**任一步失败即 `restore_snapshot` + 草稿/记忆回滚 + Run V2 `invalidate_from(reason="transaction_rollback")`**。写前有独立的 preflight 阶段闸（见 §3.1）。

**幻想作家**（`src/lib/write-pipeline.ts`）：precheck（无 key/无章/陈旧 run/任务占用→拦截）→ `beginWriteRun` 快照 → 起草 → 审 → 结算 → `commitWriteRun`；失败走 `rollbackWriteRun`/`keepPartialDraft`/`markSettlePending`。形态上已是 OpenWrite 的简化仿制，但快照存在 IndexedDB 的 `writeRuns` 字段里，没有文件级原子性。

### 1.5 审查

InkOS `continuity.ts`：基础维度编号至 33（33=章节备忘偏离），含 12 条网文结构雷点（开篇拖沓、金手指失衡、人设前后矛盾……）+ 工程维度（OOC、timeline、信息越界、hook-debt、跨章重复、词汇疲劳等）；`fanfic-dimensions.ts` 增补 34–37（角色还原度/世界规则遵守/关系动态/正典事件一致性）并按同人模式给出 critical/warning/info 矩阵。OpenWrite `skills/novel-reviewer/SKILL.md` 原文自述 ReviewerAgent 是「**33维度审计（从 InkOS 融合）**」，其 `DIMENSION_MAP` 1–37 与上述一一对应，评分公式 `100 − 20×critical − 5×warning`。**结论：审查引擎无需向 OpenWrite 借，要借的是它把审查结果做成"问题队列→修订提案→人批应用"的工作区形态**（`tools/review_store.py` + `tools/revision_service.py`，见 §3.3）。幻想作家只有单提示词 `review_chapter`，不在同一量级。

### 1.6 锁与并发（作者踩过的坑，逐行核对）

InkOS `packages/core/src/state/manager.ts`（第 8–10 行）：

```ts
const BOOK_LOCK_HEARTBEAT_MS = 30_000;
const BOOK_LOCK_LEASE_MS = 3 * 60_000;
const BOOK_LOCK_RELEASE_RETRIES = 4;
```

- `processBookLocks` 是**模块级** `Map`（同进程所有 `StateManager` 实例共享）；`acquireBookLock` 第一步查这张表，**命中即抛 `BookWriteLockError`（code `BOOK_BUSY`）**，不排队、不看租约；
- 只有**磁盘锁文件**才有自愈：同 pid 孤儿、死 pid、心跳超 3 分钟租约三种情况自动回收（`isStaleLock`，CHANGELOG v1.7.0 #337）；
- **进程内条目没有任何 TTL/看门狗**：一次卡死的 LLM 调用（管线在 `runner.ts` 持锁跑完整条链，如 `writeNextChapter` 的 try/finally）会让心跳一直刷新、租约永远新鲜，同进程内所有后续写操作全部 `BOOK_BUSY`——**直到重启 Studio**。这正是作者在《醉词》上撞到的现象；
- 全仓 **没有任何强制解锁 API/端点**（grep `unlock` 仅命中 StoryPlayer 的结局解锁 UI）；错误文案「Stale locks are recovered automatically」只对跨进程场景成立，对进程内场景是误导；
- 附带发现一个真实缺陷：Studio 的 truth 文件写入 `PUT /api/v1/books/:id/truth/:file`（`server.ts` ~5674）**直接 `writeFile`，不取书锁**，与进行中的写章存在竞态。

OpenWrite 的 `ProjectWriteLock` 只包写事务，Studio 单线程语义下问题面小；幻想作家的 `writeRuns` 软锁配合 precheck 的陈旧检测，简单但够用——两者都没有 InkOS 这种"进程内活锁"形态。

### 1.7 UI / 信息架构

- **InkOS Studio**：React SPA，hash 路由；书工作区含写作/审阅/重写工作台、Chat 生产（后台任务化，v1.7.1 起可刷新恢复、可中止）、服务配置页。作者评价「比幻想作家好用，但仍不是日常写作想要的」。**猜测（需验证）**：其大纲/骨架编辑体验偏"文件+Chat"，缺一个以"今天写哪章"为中心的连载驾驶舱。
- **OpenWrite Studio**：左侧栏（总览/大纲/正文/审稿/资料库/AI 协作 + 工具组），右侧巡查器（助手/罗盘/上下文/审稿/修订）；大纲工作区=一棵树+就地编辑详情+一次点击开写；README 明文禁止假进度条。1.7 复盘已完整拆解过其好在哪（一份真源、一份视图、每步只有一个明显下一步）。
- **幻想作家 1.7.1**：七工作区 Studio 壳；大纲区经 O1–O5 整改后收敛为一棵树+就地编辑，但整体仍是"生成下一章向导"心智包一层工作台皮，`page.tsx` 巨型编排器难以为继。

## 二、以 InkOS 为内核：取什么、修什么、弃什么

### 2.1 原样保留（内核，不动语义）

| 能力 | 锚点 |
|---|---|
| 书目录/正典布局与权威分类 | `state/manager.ts`、`interaction/truth-authority.ts`、`utils/outline-paths.ts` |
| 全套管线与 Agent 链 | `pipeline/runner.ts`、`agents/*`（architect/planner/composer/writer/settler/continuity/reviser/post-write-validator/state-validator） |
| 治理式上下文组包（protected 不压缩 + token 预算） | `utils/context-assembly.ts`（`buildGovernedRuleStack`、`applyContextBudgetIfNeeded`） |
| 原子文件集提交 + 逐章快照 + 回滚 | `utils/atomic-file-set.ts`、`StateManager.snapshotState/restoreState` |
| 33+4 维审计与 `revisionGate` | `agents/continuity.ts`、`agents/fanfic-dimensions.ts`、`models/book.ts resolveRevisionGate` |
| SQLite FTS 叙事记忆与检索 | `state/memory-db.ts`（`node:sqlite`，无原生模块负担）、`retrieval/` |
| OpenAI 兼容模型层 + 按角色 modelOverrides | `models/project.ts LLMConfigSchema`、`llm/service-presets.ts`（custom 预设）、`llm/secrets.ts`（`.inkos/secrets.json`）、`PipelineRunner.agentCtxFor` |
| 后台任务/中止传播/审批流 | v1.7.1–1.8.0 changelog 项、`POST /api/v1/sessions/:id/abort`、章 approve/reject 路由 |

### 2.2 必须在 fork 里修（桌面化前置，全部是 P0）

1. **锁的进程内自愈与强制释放**（详见 §6-G0 与 §10 风险 R1）：
   - 每次 `acquireBookLock` 登记到任务注册表（持有者任务 id、开始时间、AbortController）；
   - 新增 `POST /api/v1/books/:id/lock/force-release`：先 abort 关联任务（走既有中止传播），等待宽限期后清 `processBookLocks` 条目 + unlink 锁文件；
   - `BookWriteLockError` 携带持有者信息（已有 pid/startedAt，补任务 id/阶段），UI 能显示「谁持锁、多久、在哪个阶段」；
   - 修正误导文案：进程内冲突时不再说「会自动恢复」，改为给出中止/强制释放指引。
2. **项目根显式化**：桌面壳启动引擎时**总是**显式传根（`studio/src/api/index.ts` 已支持 `argv[2]`/`INKOS_PROJECT_ROOT`），根路径存壳配置文件；`findProjectRoot()=process.cwd()`（`cli/src/utils.ts`）这条路径在桌面形态下不允许触达。
3. **单实例语义**：见 §4。
4. **修 truth PUT 绕锁**：`server.ts` 的 truth 写入路由补 `acquireBookLock`（同文件 3071/3104/3123 行的章节路由已是正确示范）。

### 2.3 InkOS Web UX 的去留

- **保留并演进**：Studio SPA 本体（React 19 + Vite + Zustand，技术栈现代、可长期演进）；Chat 生产 + 后台任务 + SSE 进度；审阅/重写工作台；服务配置页。
- **包一层桌面壳替换掉的**：浏览器访问方式（改为 Electron 窗口，loopback-only）；`inkos studio` 的 CLI 启动心智（改为双击图标）；端口/根目录的用户可见性（全部隐藏为壳内部实现）。
- **P2 重做的**（吸收 1.7 学费，见 §9-P2）：以「连载驾驶舱」为中心的首屏（今天该写哪章、待收钩子、卷进度），大纲/骨架工作区按「一棵树+就地编辑+单一 AI 入口」重构。**不要在 P0 就动它的 UI**——先让作者用上桌面版原味 Studio，攒真实吐槽再动刀，避免重蹈 1.6 S4「只交付树皮」的覆辙。

## 三、从 OpenWrite 吸收什么（逐项：为何防漂移 → 映射到 InkOS 原语 → 不抄什么）

> 原则：**只吸收闸，不吸收运行时**。OpenWrite 的可移植资产是契约文本与机制设计（`skills/**/SKILL.md`、`OUTLINE_MARKDOWN_CONTRACT`、维度清单、craft 规则表）；一切执行逻辑必须在 TypeScript 里按 InkOS 原语重写，否则防漂移只是口号（OpenWrite 自己的结构也是"skills 描述何时调用、tools 强制执行"）。

### 3.1 大纲范围确认闸（写前硬门）

- **OpenWrite 做法**：`tools/agent/book_state.py` 的 `BookStage` 状态机——写章要求先 `confirm_outline_scope()` 进入 `CHAPTER_PREFLIGHT`，否则 preflight 直接失败（`outline_not_confirmed`）；preflight 还强制 `context.current_chapter` 存在（`missing_chapter_scope`）、上一章正文存在（`missing_previous_chapter`）（`tools/agent/orchestrator.py run_preflight`）。
- **为何防漂移**：把「AI 决定写什么」变成「人确认过的大纲节点决定写什么」，从源头锁死每章的轨道；漂移最常见的入口就是"没排纲先开写"或"写了大纲没覆盖的内容"。
- **映射到 InkOS**：InkOS 已有 `isCompleteBookDirectory`（书完整性）与 Planner 章备忘，但**写章不强制章级大纲存在**——`volume_map.md` 缺当前章条目时管线照跑。改造点：`PipelineRunner.prepareWriteInput` 前加硬校验（目标章在 `volume_map.md` 有条目、`story_frame.md`/`author_intent.md` 非空、上一章已 approve 或显式跳过），失败返回结构化原因给 UI，而非警告后继续。
- **不抄**：BookStage 全状态机与 Goethe 交接仪式（InkOS 的 Chat+propose_action 已覆盖建书确认；把整套 stage machine 搬来会和 InkOS 章状态 `ready-for-review`/approve 双轨打架）。

### 3.2 正典 diff 人闸

- **OpenWrite 做法**：`tools/agent/confirmation.py`——`CONFIRMABLE_TOOLS`（改大纲/人物/truth/世界关系等）一律两段式：预览（`unified_diff` + `preview_token` + `base_revision`）→ 用户**同轮明确**说「确认应用」→ 才允许 `confirm=true` 执行；Agent 自我确认被 `guard_confirmable_executors()` 软拦截（`explicit_user_confirmation_required`）。
- **为何防漂移**：正典是人的领土。AI 在长会话里悄悄改人设/大纲是慢性漂移的头号来源；diff 人闸让每次正典变更都被人眼看过，且 `base_revision` 防止覆盖外部编辑。
- **映射到 InkOS**：InkOS 的 `write_truth_file`（`agent/agent-tools.ts` → `interaction/project-tools.ts`）只有允许清单+锁，**没有人闸**；`propose_action` 只确认生产动作（建书/短篇/封面等），不管 truth 写入。改造点：对 `classifyTruthAuthority` 为 direction/foundation/rules 三类（含 `outline/*`、`roles/*`）的写入，Chat 途径一律改为 staged diff → SSE 推给 UI 确认卡 → 确认后带 revision 校验落盘；**管线内 Settler 对 runtime-truth（current_state/hooks/summaries）的写入不走人闸**（自动化必需，且有快照兜底）。幻想作家 `DiffConfirmGate.tsx` 的交互经验（含 1.6 P0 复查 H2 教训：提案必须落盘、不能只存前端状态）直接复用到这里——提案存 `story/runtime/proposals/`。
- **不抄**：靠自然语言关键词（「确认应用」/「ok」）判定同意——桌面 UI 用真按钮，杜绝语言歧义；会话工作记忆式的 preview token 存储（落盘）。

### 3.3 审稿 = 问题队列 → 修订提案 → 人批应用

- **OpenWrite 做法**：审查产物入 `tools/review_store.py`，Studio 审稿区按章/维度/严重度过滤问题、看证据，一键 `RevisionService.create_from_review` 生成修订提案，人看 diff 后在写锁内 apply。审查失败不自动重写，而是把书态置为 `REVIEW_AND_REVISE` 交还给人。
- **为何防漂移**：连载数月的质量稳定靠的是"问题可见、修复可控"，不是"AI 自己改到自己满意"；自动重写循环会把审查信号消耗在人看不见的地方。
- **映射到 InkOS**：InkOS 审计产物已结构化（audit 报告、`story/runtime/` trace、章状态 `audit-failed`），`ReviserAgent` 在管线内做第一轮受 `revisionGate` 约束的修订——保留；要补的是**审后人环**：审稿工作区把 continuity 维度结果做成可过滤问题队列，"生成修订提案→diff→人批"复用 §3.2 的同一套提案/确认原语。硬性规则：critical>0 的章不允许 approve（除非显式 override 并记录，见 §6-G5）。
- **不抄**：其评分公式与批量bisect实现（InkOS 审计已有自己的产出格式）；37 维清单本身（InkOS 是源头）。

### 3.4 伏笔/钩子逾期账本

- **OpenWrite 做法**：`models/foreshadowing.py` DAG（节点带 weight/layer/`target_chapter`，状态 埋伏/待收/已收/废弃）+ `ForeshadowingDAGManager.validate_dag()`（环检测、悬边、**当前章超过 target_chapter 仍未收 → 逾期**）；伏笔状态注入写作 packet，审查维度 6 兜底。
- **为何防漂移**：长篇烂尾的典型形态就是伏笔失踪；「逾期」把它从"记忆问题"变成"账本问题"。
- **映射到 InkOS**：InkOS `pending_hooks.md` + `story/state/hooks.json`（`HookRecord`，含 stale/blocked 标记，审计维度里已有 hook-debt）已是同类账本，**缺的只是 target 章位与逾期视图**。改造点：`HookRecordSchema` 增加可选 `targetChapter`（Zod schema 演进 + 状态迁移），驾驶舱显示"到期/逾期钩子"，写章 packet 中逾期钩子置顶注入，审计 hook-debt 维度把逾期升为 critical。
- **不抄**：独立 DAG YAML 文件与图结构（InkOS hooks 账本已够用，双账本必然漂移）。

### 3.5 上下文包快照（可审计的 packet）

- **OpenWrite 做法**：每章组包后把 `GenerationContext` 快照落 `context_packets/`（`orchestrator.py _write_context_packet_snapshot`），Studio 巡查器可看"AI 这章看到了什么"；预算策略显式（输入预算 = 上下文窗 − 输出预留 − 3% 安全边际，70/85/100/120% 压缩阶梯，`tools/llm/context.py ContextBudgetPolicy`）。
- **为何防漂移**：漂移排查的第一问永远是"当时喂了什么"；没有 packet 快照就只能猜。
- **映射到 InkOS**：InkOS 组包已治理化且**保护源永不压缩**（`context-assembly.ts`：intent/focus/story_frame/volume_map/current_state/hooks 属 protected），`story/runtime/` 已落 trace——改造点很小：把治理后的最终 packet（含各源截断/压缩情况与 token 计数）固化为 `story/runtime/chapter-NNNN.packet.json`，UI 提供只读查看器。
- **不抄**：其压缩阶梯参数与语义检索实现（InkOS 有自己的预算函数与 FTS 检索；OpenWrite 语义引用「不覆盖真相」的原则 InkOS 同样已遵守）。

### 3.6 Goethe/Dante 双代理心智（吸收为 UI 语言，不引机制）

- **OpenWrite 做法**：Goethe 长会话规划（想法→基础/人物/大纲草稿→确认入 `src/`→`prepare_dante_handoff`），Dante 长会话写作（确认范围→preflight→写→审→结算）；模型路由八键（`model_profiles.py ROUTE_KEYS`）。
- **映射到 InkOS**：InkOS 的 Architect（骨架）与 Planner/Writer（章）+ Chat 生产已是同构分工；吸收的是**产品语言**——UI 上把"规划模式"（改正典，一切走 diff 人闸）与"写作模式"（在轨道上产章，走管线）做成两个明确入口，沿用幻想作家品牌词（织卷=规划、落墨=写作）；模型路由用 InkOS `modelOverrides` 原生实现（planner/writer/auditor/reviser 可配不同 OpenAI 兼容端点，对应作者现有的 DEEPSEEK 主槽/FINE 精修槽习惯）。
- **不抄**：双 Agent 的交接产物文件与会话状态机。

## 四、桌面架构决策

### 4.1 三案对比与选择

| 方案 | 内容 | 判定 |
|---|---|---|
| **A. Electron 壳 + fork 的 InkOS Studio（引擎+UI）子进程** | 壳负责窗口/单实例/更新/密钥/生命周期；引擎=fork 后的 `startStudioServer`（Hono API + SPA）以 `ELECTRON_RUN_AS_NODE` 子进程跑在 loopback 钉端口；窗口加载 `http://127.0.0.1:<port>` | **✅ 选此** |
| B. 在幻想作家 Next/Electron 里重写 Studio UI，仅保留 `@actalk/inkos-core` | 保留本仓 UI 资产 | ❌ 否决：这正是 1.6–1.7 失败模式的重演（仿造别人的工作台）；且 Studio 不只是 UI——后台任务存储、SSE 广播、书创建状态机都在 `server.ts`，全部要在 Next 里再造一遍；本仓 UI 资产（巨型 `page.tsx`）恰是要淘汰的部分 |
| C. Electron 主进程内直接 embed core（无 HTTP） | CLI 已证明可行 | ❌ 否决：损失 Studio 全部现成 UI 与任务/SSE 层，工作量与 B 同级；且引擎与壳同进程后，"重启引擎清进程内锁"这个最可靠的兜底手段就没了 |

**选 A 的核心理由**：(1) 作者已认可 InkOS Studio 可用性，改造快于重造；(2) 幻想作家 `electron/main.cjs` 的基建与"拉起一个 loopback Node 服务"的形态**逐项同构**（见 4.3 映射表）；(3) 引擎独立子进程 = 锁泄漏的终极兜底（重启子进程即清 `processBookLocks`，窗口不动）；(4) `packages/core` 用 `node:sqlite`（`state/memory-db.ts` 第 75 行 `require("node:sqlite")`），核心依赖无原生模块（deps 仅 typebox/zod/js-yaml/undici/jszip/unpdf 等纯 JS），Electron 打包风险低。

**Hunch 标注（实施者必须先验证）**：
- H1：Electron 37 内置 Node ≥22 且 `ELECTRON_RUN_AS_NODE` 下 `node:sqlite` 可用（可能需 `--experimental-sqlite` 类 flag，随 Node 小版本而异）。验证法：壳内 spawn `process.execPath` 跑一行 `require("node:sqlite")`。不行则退路：给引擎捆一个独立 Node 22 运行时（体积代价），或以 `better-sqlite3` 替换 `memory-db.ts` 的驱动层（改动集中在一个文件）。
- H2：Studio 生产模式需要预构建的 `dist/`（`api/index.ts` 会在缺失时现场跑 `npx vite build`——打包版必须预构建并禁用该分支）。
- H3：pnpm workspace 依赖（core←studio←cli）打进 electron-builder 需要构建期把三包编译为 dist 并以文件依赖或打平 node_modules 方式装配；`verify:publish-manifests` 脚本说明上游已有发布形态，具体装配方式需实验。
- H4：pi-agent 两个依赖（`@mariozechner/pi-agent-core`/`pi-ai` 0.67.1）的许可证与国内网络下的安装可用性需核查（见 §10）。

### 4.2 进程模型与单实例/端口语义

```text
FantaWriter.exe (Electron 主进程)
  ├─ requestSingleInstanceLock()            ← 沿用 main.cjs 现有逻辑：二启即聚焦首例
  ├─ 读壳配置: {projectRoot, enginePort, instanceToken}
  ├─ 启动前探测: GET http://127.0.0.1:<port>/api/v1/... 健康端点
  │    ├─ 无响应 → 正常拉起引擎
  │    ├─ 响应且 instanceToken 匹配 → 残留引擎（上次未净退），提示「接管 / 结束并重启引擎」
  │    └─ 响应但 token 不匹配 → 端口被占（如作者手动跑的 inkos studio），换钉端口并醒目提示
  ├─ spawn 引擎子进程 (ELECTRON_RUN_AS_NODE=1):
  │    node studio-server.js <projectRoot>   ← 显式 argv 根，绝不依赖 CWD
  │    env: INKOS_STUDIO_PORT=<pinned>, FW_INSTANCE_TOKEN=<token>
  ├─ BrowserWindow → http://127.0.0.1:<port>
  └─ 退出: 先 abort 所有任务 → 等引擎优雅落盘 → kill 子进程（防止残留 4567/4568 式幽灵）
```

- **端口**：沿用幻想作家「首启扫描空闲端口→钉进配置」模式（现 `APP_DATA_PORT`，默认 17831 起）——**放弃 4567 缺省**，从根上避开与作者手动跑的 InkOS 冲突；实测确认 InkOS 无 EADDRINUSE 自动+1 逻辑（4568 只能是人为二启），新壳必须保证同一项目根全局最多一个引擎。
- **项目根**：默认 `%USERPROFILE%\Documents\幻想作家\`，首启向导可改；根内即标准 InkOS 项目布局（`inkos.json` + `books/` + `.inkos/secrets.json`），**作者用文件管理器/Git 可直接触达全部正典**——这本身就是从 IndexedDB 时代的一次重大升级。
- **引擎健康与重启**：壳持续心跳健康端点；「重启引擎」作为一级菜单动作（锁兜底 + 更新引擎后热换）。

### 4.3 幻想作家壳资产 → 新壳映射表

| 现有资产（`electron/`） | 去向 |
|---|---|
| `main.cjs` 单实例锁、窗口生命周期 | 原样迁移 |
| 钉端口 + `waitForServer` 健康检查（现打 `/api/generate`） | 改打引擎健康路由（如 `/api/v1/project`，具体路由实施时定） |
| `ELECTRON_RUN_AS_NODE` 拉 Next `server.js` | 改拉 fork 的 studio server 入口 |
| `config.env`（`APP_CONFIG_PATH`，icacls ACL） | 保留存壳级配置（根路径/端口/更新 token）；**模型密钥改存 InkOS 原生 `.inkos/secrets.json`（项目根内，加入项目 `.gitignore` 模板）**，避免双套密钥体系 |
| `update-search.cjs`/`github-release.cjs`/`setup-artifact.cjs`（静默本地目录 vs 手动 GitHub、SHA256、GFW 规避） | 原样迁移，安装包名沿用 `FantaWriter-Setup-x.y.z.exe` |
| NSIS electron-builder 配置、CI「拒绝密钥进安装包」闸 | 原样迁移适配 |
| Next.js standalone、`src/` 全部渲染层与 `src/lib` 业务 | **退役**（`src/lib` 的组包/管线思想已被 InkOS 内核超集覆盖；仅迁移器复用其类型定义，见 §7） |

### 4.4 仓库形态

新幻想作家 = 本仓重构为 AGPL-3.0 monorepo：`packages/core`、`packages/studio`（自 InkOS fork，保留 git 历史与上游 remote 以便合流）、`packages/desktop`（新：Electron 壳，迁自 `electron/`）、`packages/migrator`（新：迁移器）。CLI 包可裁剪（桌面形态不需要，但保留对调试有利；倾向保留，实施者定）。品牌层（应用名、窗口标题、about、安装包名）统一为 幻想作家/FantaWriter；引擎层保留 InkOS 署名与版权头（AGPL 义务，见 §8）。

## 五、端到端连载流程（作者实际点击的路径）

> UI 词汇沿用本仓品牌：织卷=规划/正典 Agent，落墨=写章管线。以下每步标注落盘产物与失败面。

### 5.1 首启（一次性）

1. 装 `FantaWriter-Setup-2.x.exe` → 双击图标；
2. 首启向导：选/建项目根（默认 文档\幻想作家）→ 配模型（Base URL + Key + 模型名，OpenAI 兼容；「测试连接」必须真调一次）→ 可选按角色分配（规划/写作/审计用不同模型）；
3. 落盘：`inkos.json`（llm 配置+modelOverrides）、`.inkos/secrets.json`（key，0600 语义/ACL）、壳 `config.env`（根路径、钉端口）。

### 5.2 新书 → 骨架（人握方向盘）

1. 「新建书」→ 表单（书名/题材/一句话前提/结局方向）或与织卷对话展开；建书动作走 InkOS 既有 `propose_action` 确认卡；
2. Architect 生成五件套：`story_frame.md`（含结局方向）、`volume_map.md`（第一卷 OKR+章级规划）、`roles/`、`book_rules.md`、`author_intent.md`；
3. **骨架检查台**（新 UI，P1）：五件套逐一过目、就地编辑（人的直接编辑=直写并记录；AI 建议的修改=diff 人闸）；
4. 书就绪判定 = `isCompleteBookDirectory` + G1 前置项齐备；未就绪时「写下一章」按钮禁用并列出缺项（**不可用的动作不摆出来骗点击**——OpenWrite 学费）。

### 5.3 日常写章（核心循环，每天走一遍）

```text
打开应用（单实例，自动回到上次的书）
→ 驾驶舱：下一章 N「章标题/卷内位置」· 本卷 OKR 摘要 · 到期/逾期钩子 · 昨日章状态
→ 点「写下一章」
   ├─ G1 硬校验失败 → 结构化提示（如"volume_map 无第 N 章条目"）+ 一键跳转排纲
   └─ 通过 → 后台任务启动（书锁被本任务持有，UI 显示锁徽标）
→ 运行面板（SSE 实时）：计划 → 组包 → 起草 → 审计 → 修订 → 结算
   ├─ 每阶段真实进度（禁假进度条），packet 快照生成后即可点开「本章 AI 看到了什么」
   ├─ 「取消」→ abort 传播 → 已写内容按管线语义回滚/留草稿，锁释放
   └─ LLM 故障 → 明确报错（分类：网络/配额/密钥/上游），任务终止，锁释放
→ 章完成，状态 ready-for-review → 审稿面板
   ├─ 问题队列（维度/严重度过滤，critical 置顶，证据定位到段）
   ├─ 正文阅读 + 逐段修订提案（AI 提案走 diff 预览）
   ├─ 「通过」→ approve（G4 定稿；critical>0 时按钮禁用，需先修或显式 override）
   ├─ 「打回重修」→ ReviserAgent 定向修订 → 回到队列
   └─ 「回滚本章」→ 快照恢复（snapshots/<n>），章文入 .trash
→ 驾驶舱刷新：下一章变为 N+1；钩子账本/current_state 已由结算更新
```

### 5.4 失败 / 取消 / 锁 UI（必须显式设计的非快乐路径）

| 场景 | 行为 |
|---|---|
| 写章中关窗 | 提示「落墨任务进行中」：等待完成（后台任务在引擎进程里活着）/ 中止并退出；禁止静默杀进程留下锁文件 |
| `BOOK_BUSY`（409） | 弹「本书正在被写入」卡：显示持有任务、阶段、已持续时长 + 「中止该任务」/「强制释放」（二次确认）/「重启引擎」（兜底，三层递进） |
| 引擎崩溃/断电 | 重启后磁盘锁按 #337 规则自愈（死 pid/超租约）；驾驶舱提示「上次任务未完成」，指向快照回滚或续写 |
| 双开应用 | Electron 单实例：二启即聚焦已开窗口 |
| 作者同时手动跑上游 `inkos studio` 指向同一根 | 引擎探测到 `.write.lock` 非本进程活跃持有时按跨进程租约语义处理（既有行为）；壳在文档与首启向导明示"同一项目根只跑一个引擎" |
| 排纲/改正典与写章并发 | 正典写入同样取书锁（含修掉的 truth PUT 绕锁），后到者收到 BOOK_BUSY 卡片而非静默失败 |

### 5.5 过卷

卷尾（volume_map 本卷 OKR 完成）→ 驾驶舱出现过卷提示 → 织卷起草下一卷 OKR/章规划 → **diff 人闸确认**写入 `volume_map.md` → 继续 5.3 循环。（过卷是里程碑仪式，入口只在此时出现——1.7 复盘教训：低频仪式不常驻高频页面。）

## 六、防漂移硬闸（G0 地基 + G1–G6 六道，全部是"不满足即拒绝"，不是标签）

> "硬闸"的定义：**代码路径上不存在绕过分支**；违反时返回结构化拒绝，UI 呈现原因与出路。每道闸给出实现锚点与验收口径。

**G0 · 锁与单写者闸**（其余闸的地基）
- 规则：同一书任一时刻至多一个写入者；锁必须三层可恢复（中止任务 → 强制释放 → 重启引擎）。
- 锚点：`state/manager.ts` fork 改造 + 任务注册表 + force-release 路由（§2.2）；壳单实例 + 退出杀引擎（§4.2）。
- 验收：写章进行中，任何第二写入操作收到 BOOK_BUSY 卡片；人为挂起 LLM（断网模拟）后，三层恢复手段全部在 120 秒内让书恢复可写；重启引擎后无残留锁文件。

**G1 · 大纲/意图闸**（写前）
- 规则：目标章在 `volume_map.md` 无条目、或 `story_frame.md`/`author_intent.md` 缺失为空、或上一章未 approve（且未显式选择"带病续写"）→ 拒绝启动写章。
- 锚点：`PipelineRunner.prepareWriteInput` 前置校验（§3.1）。
- 验收：删掉 volume_map 中第 N 章条目 → 「写下一章」被拒且提示指向排纲；补上后放行。

**G2 · packet 边界闸**（组包）
- 规则：protected 源（intent/focus/story_frame/volume_map/current_state/hooks）永不压缩截断；预算不足时只压缩 compressible 历史；packet 快照必落盘。
- 锚点：`utils/context-assembly.ts` 既有语义 + 新增 `chapter-NNNN.packet.json` 固化（§3.5）。
- 验收：构造超长历史书 → 检查 packet 快照中 protected 源完整、压缩发生在历史摘要段；UI 能打开任一章的 packet 查看器。

**G3 · 正典 diff 人闸**（Chat 改正典）
- 规则：Agent 对 direction/foundation/rules 类文件（`author_intent`/`current_focus`/`outline/*`/`roles/*`/`book_rules`）的一切写入必须经 staged diff + UI 按钮确认 + base revision 校验；提案落盘（`story/runtime/proposals/`），刷新不丢。
- 锚点：`interaction/project-tools.ts` 写入口插闸 + Studio 确认卡（§3.2）。
- 验收：让织卷"顺手"改人设 → 出现 diff 卡且文件未变；确认后落盘且记录；期间外部编辑过该文件 → revision 冲突提示而非覆盖。

**G4 · 原子提交闸**（落盘）
- 规则：章文+投影+结构化状态必须经 `commitAtomicFileSet` 一次性提交；任何阶段失败不得留半状态；approve 前章不算定稿，回滚必走快照。
- 锚点：既有 `atomic-file-set.ts` + `snapshots/` + approve 路由；补审稿 UI 的回滚入口。
- 验收：结算阶段人为 kill 引擎 → 重启后书状态一致（章文与 state 要么都在要么都不在）；回滚第 N 章后 `current_state`/hooks 与 N-1 章快照一致。

**G5 · 审查闸**（定稿前）
- 规则：审计必跑（`reviewMode` 桌面版不暴露"跳过"为缺省项）；critical>0 → approve 按钮禁用；override 必须显式勾选并写入章 meta（who/when/why），驾驶舱可见带病定稿标记。
- 锚点：`chapter-review-cycle.ts` + `revisionGate(strict)` 缺省 + 审稿工作区（§3.3）。
- 验收：构造 OOC 章 → critical 出现 → 无法直接通过；override 路径留痕可查。

**G6 · 写作禁令闸**（文本层）
- 规则：`book_rules.md` 禁令 + 确定性 post-write 检查（章号引用、AI 痕迹模式、敏感词）违规 → 强制进修订，修订仍违规 → 章置 audit-failed，不得 approve。
- 锚点：`agents/post-write-validator.ts`、`sensitive-words.ts`、`rules-reader.ts`；OpenWrite `craft/ai_patterns.yaml`/`humanization.yaml` 的禁语/AI 痕迹规则表（Apache-2.0，可带 NOTICE 吸收）合并为 fork 缺省 craft 配置。
- 验收：book_rules 加一条自定义禁令 → 违规章被拦；缺省规则表能拦住「不是…而是…」式 AI 痕迹样例。
